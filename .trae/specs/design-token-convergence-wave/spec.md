# 令牌波（Design Token Convergence）· 方案（spec）· 2026-09-25

> **性质（用户 2026-09-25 拍板）**：**方案文档先行** —— 本文件是**讨论载体**，未拍板前**不动任何样式/令牌代码**。
> **判据纪律**：本文件每条结论都附**可复现证据**（命令或文件:行）；无证据的一律进「未验证项」。引"文档说已实现"不作为证据。
> **范围**：`client/`（uni-app x **App-Android 单端**）。**不含**：小程序/Web、dark mode（见 §7）。

---

## 0. 一句话

把 32 个内联 `<style>` + 6 个外置 css（合计 **7400 行**）里的 **~960 个颜色位点**与尺寸/字号/间距，收敛到 `client/design_tokens.json` **单一真源**，使令牌机制覆盖率从 **0%（实测）** 提升到**可门禁**，并保证**像素级视觉零差异**。

| 维度 | 实测值 | 证据命令 |
|---|---|---|

| 其他颜色形态 | **`rgb()/rgba()` 190 处、`linear-gradient()` 10 处** | 同上 |
| **颜色位点合计** | **≈962** | 762+190+10 |
| 高频色 Top6 | `#3a2e25`×152、`#8a7a6a`×94、`#ffffff`×94、`#b05a3a`×93、`#b3a696`×88、`#c4913c`×56（占 ~63%） | 同上 |

| `design_tokens.json` | 5 组 / **52 个叶子值 / 1550 字节** | `client/design_tokens.json` |

### 1.1 五个结构性差异（决定方案的关键，比"数字大小"重要）

1. **单位口径不一致（最容易踩的坑）**：`design_tokens.json.dimensions` 是 **390 画布 px**（`page_width:390 / card_radius:20 / tabbar_height:62`），而代码样式全部用 **rpx（750 基准）**。二者**不是 1:1**（×750/390≈1.923）；且现有 rpx 值多为整齐数（说明是人手写的，不是从 px 换算来的）⇒ **"补令牌集"必须先定基准（750 rpx 还是 390 px）与换算规则**。
2. **令牌集覆盖不足**：52 个值 vs 颜色位点 962 个 —— 尤其 **`rgb()/rgba()` 190 处与 10 处渐变在令牌集里完全没有建模**（透明色阶、渐变、阴影全缺）。
3. **语义层级缺失**：现有 tokens 是"用途/色相混写"的**单层**（`bg_page`/`bg_card`/`accent_rust`/`accent_amber`…），没有 DTCG 那套 `原始色阶 → 语义别名` 两层 ⇒ **语义 token 无法表达**（例：`color.text.primary` → `{color.neutral.900}`）。
4. **19 处 `:style=` 动态绑定**：颜色/尺寸是运行时拼进 template 的（如进度条 `width: (p*100)+'%'`、`idle-color="#C4913C"`）⇒ 静态 CSS 替换覆盖不到，需**单独一簇**处理。
5. **`effects.card_shadow` 不是合法 CSS**：值形如 `"0 4 16 #00000008"`（空格分隔 + 8 位 hex alpha）⇒ 需转换器产出合法 ucss 阴影。

## 2. 平台能力（官方文档 + 本仓实锤）

| # | 结论 | 证据 |
|---|---|---|
| 1 | ✅ App 平台 ucss **支持 `var()`**（与 `url()`/`rgb()`/`rgba()`/`env()` 同列） | 官方《uvue css 使用》css 方法章 |
| 2 | ✅ 官方**示范的声明位是 `class`**（不是 `:root`）：在 **`app.uvue` 全局样式**里 `.theme-x { --text-color: #333 }`，"除非样式隔离策略禁止，页面可直接使用这些 class" | 官方《暗黑主题适配》方案③/④ |
| 3 | ✅ 页面根元素**内联绑定变量**亦可行：`:style="--a:#fff"` + `color: var(--a)`；本项目**已有 19 处 `:style` 在用**，机制在 App 端可用 | 官方主题教程 + 本仓实测 |
| 4 | ❌ **`:root` / `page` 选择器不可用**（只支持 class 选择器）；全仓 `:root`/`page{` 使用数 = **0**（无人试过） | 官方 ucss 限制 + 本轮 grep |
| 5 | ⚠️ **本仓实锤：App 端样式不继承**（`App.uvue` 有"**勿改回**"级注释：连 `font-family` 都必须逐 `text` 类手写） | `client/App.uvue:95-113` |
| 6 | ⚠️ `theme.json` **只管 pages.json/tabbar 样式，不管页面 css** ⇒ 对本波主体无用（但 tabbar/nav 颜色可顺带收敛，属另一小簇） | 官方《theme.json》 |

### 2.1 未验证项（V1–V3，**本方案的成败全在这里**）

- **V1 · 变量作用域**：在"样式不继承"（#5）的前提下，变量随 class/inline style 挂到元素后，**后代元素的 `var()` 能否解析**？还是**只在同一样式块内可见**？
- **V2 · 跨文件可见性**：外置 `.css`（经 `@import`）内的 `var()` 能否解析到 `app.uvue` 全局 class 里声明的变量？
- **V3 · `@media (prefers-color-scheme)` + 变量覆盖**在本仓 HBuilderX 版本是否可用（决定"是否给暗色留门"）。

> 为什么必须实测：**编译不报错 ≠ 变量生效**（本波已有同类实锤——GAP-1/样式外置都出现过"编译绿但实际不生效"）。且这类失败的表现是**视觉塌陷/回退默认值**，静态门禁抓不到，只能靠探针 + 产物 bytes + **目视**。

## 3. 方案候选与对比

| 方案 | 做法 | 改动面 | 换肤能力 | 回滚粒度 | 前置依赖 | 风险 |
|---|---|---|---|---|---|---|
| **A** 全局 class 变量 + `var()` | `app.uvue` 定义 `.theme-light{--…}`，各文件把字面量改 `var(--…)` | 小（逐值替换） | ✅ 有 | 逐文件 | V1/V2 必须成立 | 变量不解析=整页视觉塌陷，编译不报错 |
| **B** 构建期令牌编译 | 脚本（DTCG 源 → 生成字面量）替换 ucss 里的值 | 中（需生成链 + 纳入门禁） | ❌ 无（静态） | 全量（重跑生成） | 无（不依赖平台） | 与"人工抄写"的 diff 巨大；失去运行时换肤 |
| **C** 混合 | 颜色/尺寸走 A；19 处 `:style=` 走 `styles/tokens.uts` 常量；tabbar/nav 走 `theme.json` | 中 | 部分 | 分簇 | V1/V2 成立 | 三套机制并存，需清晰边界 |

**推荐路径**：**先跑 V1–V3 探针 → 若通过走 A（19 处动态与 tabbar 按 C 拆簇）→ 若 V1/V2 不通过则退 B**。

**关于前沿标准（值得采纳的部分）**：W3C DTCG **Format Module 2025.10 已于 2025-10-28 成为首个稳定版**（`$value`/`$type` + `{color.blue-600}` 别名），Style Dictionary v4 / Terrazzo / Figma / Tokens Studio 均读写该形态。本项目 `design_tokens.json` **不是** DTCG 形态（扁平 `key:value`，无 `$type`）⇒ 建议**升级为 DTCG 形态**（拿到别名能力 + 类型化转换 + 与设计工具互通）；但**不建议引入 Style Dictionary/Terrazzo 本体**——它们的价值在"一份源产多端"，本项目为**单端**，自写 ~100 行转换器（DTCG → ucss 变量表 + 换算）成本更低、可控性更高。

## 5. 验收口径（**不含"看起来对"**）

1. **冷编译**：`HBuilderX cli launch app-android --compile true` → `项目 client 编译成功`（**必要非充分**，参见 GAP-1/GAP-2）。
2. **产物取证**：`unpackage/**/bytes/*.style.bytes` 含目标类名与**变量解析后的期望值**（B5d/B5.2e 先例）。
3. **目视真机**：像素级比对（颜色/圆角/阴影/渐变零差异）——**当前 `adb` 无设备 ⇒ 此条为阻塞项，必须显式标注，不得以冷编译冒充**。
4. **门禁**：P4 的棘轮（字面量只减不增）+ 反向探针（临时加一个字面量 → CRITICAL）。
5. **逐文件 diff**：仅允许"字面量 → `var(--x)`"改写，禁止结构变更（若必须改结构，另开单条说明）。

## 6. 风险与回滚

- **主风险**：V1/V2 不成立时，`var()` 静默不解析 → 视觉回退默认值/塌陷，而**编译与静态门禁全绿**。缓解：P2 探针先证；P3 逐批目视。
- **次风险**：单位基准选错（px↔rpx）造成全端尺寸漂移；缓解：P1 用"现有 rpx 值的分布"反推基准（整齐数 4/8/12/16/20/24 与 tokens.spacing 同构，佐证基准=750）。
- **回滚**：令牌源与样式**物理分离**，每批独立提交、可单批 `git revert`；P1（纯数据）零风险。

## 7. 待拍板（本文件的存在目的）

1. **令牌集是否升级为 DTCG 形态**（`$value`/`$type` + 别名）？——建议**是**（拿别名与类型化转换，且为将来小程序/Web 铺路）；若否，则退回自定扁平形态并放弃工具互通。
2. **是否同意"先 V1–V3 探针、再在 A/C 间定"**？——建议**是**（避免在错误机制上做 7400 行迁移）。
3. **基准单位定 750rpx 还是 390px**？——建议**750 rpx**（与现有代码同基准，减少换算面）；`design_tokens.json` 的 px 值作为"画布口径"保留为**输入**而非输出。
4. **分期是否按 P1→P5**？是否**先只做 P1（纯数据、零风险）**？
5. **dark mode 明确不做**？——建议：**本波不做**，但 V3 探针顺带验一次（决定是否"留门"）。
6. **时间点**：P3 的目视验收需要设备；在设备到位前，P1/P2/P4 可做，P3 只能做到"编译+产物取证"，**目视挂账**。
