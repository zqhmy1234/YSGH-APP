### 为什么转成 16k 单声道 wav

- 规格 `docs/真值数据规格标准_v1.md:400` 写明 `audio_ref` 仅接受 **wav/m4a**，mp3 不在允许集；
- 客户端录音实测 `sampleRate: 16000`（`client/uni_modules/yishu-recorder/utssdk/app-android/index.uts:216`），
  转成同口径才能在 WER 校准里**可比**（采样率不同会引入额外误差，把算法问题误判成数据问题）。

## 三、⚠️ 三个必须先说的缺口（不掩盖）

1. **没有 xlsx 标注表** ⇒ 无法生成 `c_v1.json`。
   按规格，`transcript` 必须是**人工校对**文本（`transcript_source=human`）才算真值，
   机器转写只作参考。本次只收到音频，**没有转写/情绪/噪音标注**。
   已验证：`python scripts/validate_truth_data.py` → 「批 c: 0 条」（校验器通过是因为它允许暂缺）。
2. **3 段超时长上限**：`c-0001` 373.8s、`c-0004` 352.7s、`c-0008` 274.6s，
   而规格硬约束是 **≤210s**（`convert_truth_xlsx.py:764` 会把越界条目 `ENUM_INVALID` 跳过）。
   **未擅自切割**——切在哪里是人工判断（切在句中会破坏转写与音频的对齐），需产品部定。
3. **`user_id_hashed` 无法计算**：需要采集时的 salt；规格要求同一用户跨批哈希一致，
   不能凭空生成（salt 变了哈希就变，跨批一致性直接破坏）。

## 五、对 RAG 评测的意义（为什么值得等这批）

C 批是**文档集（语料）**，与 B/D 批同属「被搜索的记忆内容」。
当前 RAG 真值评估用的是**合成语料 131 条 / 1273 字**——已实测这个规模会让
任何词面判据（OOV/覆盖率）假失败（`产品`/`道理`/`美食` 在 1273 字里都不存在），
而真库 58643 字上同一判据**正样本 0 误杀、负样本 10/10 全挡**。
⇒ C 批转写文本一旦到位，就能把 A-06 的评测从合成语料换到真实规模，
不必等「扩语料」这个含糊前置。
