### 1.3 已发现的真实缺口

三张照片均只有 EXIF tag `306`（`DateTime`），没有 `36867`
（`DateTimeOriginal`）。当前 `backend/app/services/photo_exif.py` 只读取
`DateTimeOriginal`，因此项目现有解析函数对三张样本返回的拍摄时间全部是
`None`，而 GPS 能正确解析前两张。

这条必须先修，否则后续会用保存时间冒充拍摄时间，或把“解析器不兼容”
误判为用户数据没有拍摄时间。

## 三、P0-1：照片拍摄时间与地点

### 3.1 数据口径

| 字段 | 定义 | 用途 |
|---|---|---|
| `taken_at` | 照片或内容实际发生的时间 | 时间轴排序、日卡归属、事件聚合 |
| `created_at` | 用户保存或上传内容的时间 | 审计、排障，不用于时间轴主口径 |
| `updated_at` | 卡片编辑时间 | 不同步为拍摄时间 |

照片时间和地点优先级：

```text
EXIF DateTimeOriginal
  → EXIF DateTime（兼容真实相机）
  → 相机新拍时记录的拍摄时刻
  → 未知，不拿保存时间冒充
```

地点优先级：

```text
照片 EXIF GPS
  → 按下快门时的实时定位（仅相机新拍）
  → 无值，地点留空
```

相册旧照片不得使用上传时当前位置兜底。

### 3.2 前端流程

1. 用户选择照片后，不再统一把 `takenAt` 写成 `Date.now()`。
2. 相机新拍与相册选图使用独立入口，保留来源类型：
   - `camera`：允许记录快门时点与当时定位；
   - `album`：只信任文件 EXIF，拿不到就标记未知。
3. 上传前显示“拍摄时间读取中/未知”的诚实状态。
4. 上传完成后，用服务端最终 `taken_at`、`place` 覆盖本地临时值。
5. 刷新时间轴和事件缓存，避免旧卡继续显示上传时间。
6. 卡片编辑标题、标签、备注只更新 `updated_at`，不得改 `taken_at`。

### 3.3 后端配套

1. 扩展 EXIF 时间兼容：
   - 优先 `DateTimeOriginal`；
   - 缺失时回退 `DateTime`；
   - 都按相机本地时间 `UTC+08:00` 解释。
2. 分片上传完成路径与 multipart 路径统一走同一个 EXIF 解析器。
3. EXIF 时间优先于客户端 meta；客户端值只作兜底。
4. EXIF GPS 优先于客户端当前位置；无有效经纬度时不得根据 GPS 时间/CELLID 猜坐标。
5. 逆地理在入库后统一将 WGS84 转 GCJ-02，再请求高德。
6. `place` 为空是合法结果，前端不得显示默认城市。

### 3.4 真机验收

|---|---|---|
| GEO-01 | 选择 2025 年旧照片 | 显示 `2025-06-12 16:21:31` |
| GEO-02 | 同一张照片在另一个地点保存 | 地点仍来自照片 GPS，不来自当前位置 |
| GEO-03 | 选择 2026-09-26 无 GPS 照片 | 时间正确，地点为空 |

## 四、P0-2：关键词搜索与卡片召回

### 4.1 关键词定义

精确关键词按以下范围匹配：

1. 内容原文；
2. 语音转写；
3. 照片 OCR；
4. 照片 AI caption；
5. 事件/记忆卡标题；
6. 标签。

排序优先级：

```text
内容原文 >
OCR/语音转写/照片描述 >
事件卡标题 >
标签 >
纯语义相似
```

标签和事件标题允许命中，但必须标记命中来源。客户端菜单名、页面路由名不作为记忆搜索条件。

### 4.2 后端流程

1. 查询归一化：首尾空白、全半角、英文大小写、常见标点。
2. 建立独立精确召回：
   - 完整短语包含；
   - 多词组合；
   - 始终按 `user_id`、软删除、敏感规则过滤。
3. 精确召回与 Qdrant 语义召回合并，不因向量 Top-K 截断丢失关键词结果。
4. 同一 `content_id` 去重；按命中来源加权。
5. 返回 `trace.matched_fields`，例如 `text`、`ocr`、`event_title`、`tag`。
6. Qdrant 有噪声结果时也要补精确召回，不能只在零结果时兜底。

### 4.3 前端流程

1. 输入关键词并确认。
2. 先显示当前结果或骨架，不清空旧列表。
3. 服务端返回后按“事件记忆卡”展示：
   - 标题；
   - 摘要；
   - 时间、地点；
   - 命中来源；
   - 相关照片/语音入口。
4. 同一事件的多个内容命中合并成一张卡，使用 `event_id` 去重。
5. 点击卡片进入事件或对应内容定位。
6. 无结果时提示换说法，并区分“系统降级”。

### 4.4 可借鉴功能分支

- `client/composables/useSearchState.uts`
- `client/components/TabSearch/SearchHitOps.uvue`
- 搜索历史、筛选、空结果建议、结果操作

只借鉴前端状态与交互；后端关键词召回必须单独修复。

### 4.5 验收

| 编号 | 查询 | 预期 |

| SR-01 | 内容原文中的完整词 | 对应卡命中，来源=原文 |
| SR-02 | OCR/caption 中的词 | 对应照片卡命中 |

## 五、P0-3：从已有记忆重建画像

第一阶段不导入外部 CSV/JSON，只从用户已有完成内容重建。

### 5.1 后端任务

1. 新增重建任务与状态接口：
   - `POST /api/v1/profile/rebuild`
   - `GET /api/v1/profile/rebuild/{job_id}`
2. 仅扫描当前用户、状态为 `done` 的内容。
3. 分批调用现有 `profile_annotator`，保存来源 `content_id` 与证据。
4. 幂等：相同证据重复执行不重复累计。
5. 支持 `queued/running/completed/failed`、已处理/总数/失败数。

### 5.2 前端流程

1. 绘制管理页增加“从已有记忆重建画像”。
2. 点击后创建任务并显示进度。
3. 完成后重新拉取画像并展示：
   - 用户可读的维度值，不显示内部字段名；
   - 依据记忆数；
   - 最后更新时间。
4. 保存新记忆时可触发增量刷新，但必须防重复。
5. 空态区分“仍在加载”和“确实没有足够记忆”。

### 5.3 可借鉴功能分支

- 画像证据条数；
- “暂无…”空态防闪现；
- 深链进入时返回壳的兜底。

功能分支没有全量画像重建任务，不能误认为已实现。

## 六、P0-4：语音记录转写

### 6.1 先定位阻塞层

按顺序确认：

1. 录音文件是否落盘且大小正常；
2. 上传是否成功、`contents.status` 是否完成；
3. 当前 ASR provider、模型或 Key 是否可用；
4. worker 是否消费转写任务；
5. 后端返回文本后，客户端是否正确解析和回填；
6. 转写文本是否写入搜索索引。

### 6.2 实现流程

```text
录音中
  → 音频已保存
  → 上传完成
  → 转写排队
  → 转写中
  → 转写完成 / 失败待重试
```

1. 音频先可靠保存，再异步转写。
2. 优先复用项目已有本地 ASR；本地不可用时再走配置有效的云端 ASR。
3. 无模型、无 Key 时明确失败，不生成假文字。
4. 失败保留音频，提供“重新转写”。
5. 转写成功后：
   - 回填正文；
   - 更新时间轴；
   - 更新搜索索引；
   - 允许情绪和画像链路使用真实文本。

### 6.3 验收

| 编号 | 场景 | 预期 |
|---|---|---|
| VO-01 | 5–15 秒普通话 | 显示对应文字 |
| VO-02 | 无网络录音 | 音频不丢，恢复后可重试 |
| VO-03 | ASR 不可用 | 明确失败，不显示空白正文 |
| VO-04 | 转写成功 | 搜索该文字能命中语音卡 |
| VO-05 | 音频与文本时间 | 保持一致 |
