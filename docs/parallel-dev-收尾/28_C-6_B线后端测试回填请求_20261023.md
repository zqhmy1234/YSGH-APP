## 一、请求目的

C-6 台账当前已完成全量编号归集，但 API、RET、AGG、CLS、PRF、SAF、AUTH 等纯后端项目仍需要 B 线提供执行状态。C 线只做归集和缺口标注，不重复执行后端 pytest，也不根据代码推断测试通过。

请 B 线按台账中的测试编号逐项回传，结果统一使用四态：

- 已过
- 未过
- 未执行
- 不适用

## 二、每项必须提供的信息

| 字段 | 要求 |
|---|---|
| 测试编号 | 与 C-6 台账一致，例如 API-xxx、RET-xxx、AGG-xxx |
| 四态结论 | 已过 / 未过 / 未执行 / 不适用 |
| 证据 | pytest 用例名、测试文件路径，或 tracker 条目 |
| 执行时间 | 至少精确到日期 |
| 基线版本 | Git commit 或分支；本轮应尽量基于 `f49df29` |
| 未通过说明 | 实际结果、报错摘要和影响范围 |
| 未执行原因 | 缺环境、缺数据、缺前置或被产品口径阻塞 |

只有“结论 + 可定位证据”齐全时，C-6 才回填为最终状态。

```text
测试编号：API-001
```

## 四、范围与优先级

优先级从高到低：

1. 最新 `f49df29` 基线上与本轮分类扩展、RAG 拒答相关的测试。
2. 搜索、聊天、事件、回响、照片上传、敏感画像和消息中心相关测试。
3. API、RET、AGG 主链路。
4. CLS、PRF、SAF、AUTH 等支撑能力。
5. 需要外部服务或历史数据、当前无法执行的测试。

## 五、回传后的处理

C 线收到结果后将：

1. 更新 C-6 四态统计和逐行证据。
2. 把未通过项拆成可复现问题或缺口。
3. 将 C-5 中依赖后端能力的条目更新或继续挂起。
4. 在周报中区分 C 线真机结论与 B 线 pytest 结论，避免混写。
