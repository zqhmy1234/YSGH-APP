# 视觉/多模态调用的供应商守卫缺陷（2026-10-16）

> **给 `LLM 供应商解耦（DeepSeek）` 那笔改动（台账 §7.27）的作者**
> —— 改动本身没问题，但它顺带把一个**共用的守卫**改成按供应商判定，
> 而**视觉调用恒走百炼**，于是守卫的语义对不上了。

---

## 一句话

`_llm_available()` 现在按 `settings.llm_provider` 判定（这对**文本**调用是对的），
但 `image_caption` / `embed_image` / `embed_text_in_vision` 这三个**视觉调用也用它当守卫** ——
而它们**恒走百炼**（你们注释里自己也写了「DeepSeek 无视觉模型」）。

⇒ 一旦有人把 `LLM_PROVIDER` 切成 `deepseek`，视觉调用会**拿另一家的 key 判定**。

---

## 证据

**`backend/app/services/external/dashscope.py`（现行）**

```python
def _llm_available() -> bool:
    """LLM 可用判定：非 mock 且**所配供应商**已配 key（2026-10-15 · 台账 §7.27）
    ⚠️ 刻意不看"另一家"的 key：切到 deepseek 后，即便 dashscope key 有效也不得算可用
    """
    if settings.mock_external_ai:
        return False
    if settings.llm_provider == "deepseek":
        return bool(settings.deepseek_api_key)      # ← 看的是 DeepSeek 的 key
    return bool(settings.dashscope_api_key)
```

**三个视觉调用全是同一句守卫**（`image_caption` / `embed_image` / `embed_text_in_vision`）：

```python
    if not _llm_available():
        raise RuntimeError("百炼未配置，图片塔不可用（需 DASHSCOPE_API_KEY）")
    from dashscope import MultiModalConversation   # ← 实际调的是百炼 SDK
    ...
```

## 失效矩阵

| `LLM_PROVIDER` | `DASHSCOPE_API_KEY` | `DEEPSEEK_API_KEY` | `_llm_available()` | 视觉调用实际行为 |
|---|---|---|---|---|
| `dashscope`（默认）| ✅ | — | True | ✅ 正常 |
| `dashscope` | ❌ | — | False | ✅ 正确报错 |
| **`deepseek`** | ✅ | ❌ | **False** | ❌ **误报「百炼未配置」** —— 明明有可用的 dashscope key |
| **`deepseek`** | ❌ | ✅ | **True** | ❌ **守卫放行**，到 SDK 调用处才炸，且错误信息是「百炼未配置」——**误导排查** |
| `deepseek` | ✅ | ✅ | True | ✅ 碰巧能用 |

**影响面**：只有 `LLM_PROVIDER=deepseek` 时暴露。**默认 `dashscope` 下行为与改动前完全一致，零影响** ——
所以这不是"现在坏了"，是"**切过去那天会坏**"，而且**坏得不容易查**（错误信息指向错误的 key）。

受影响的三个调用：
- `image_caption`（照片 caption —— B2-4 以图搜图索引/检索的必经路径）
- `embed_image` / `embed_text_in_vision`（R-4 真图片塔，`tongyi-embedding-vision-plus`）

---

## 建议修法

**给视觉调用一个独立的守卫**，语义直白：

```python
def _vision_available() -> bool:
    """视觉/多模态调用的可用判定 —— **恒看百炼**，与文本供应商无关。

    为什么必须单独一个：`_llm_available()` 按 `settings.llm_provider` 判定（文本调用用），
    但视觉调用（Qwen3-VL caption / tongyi-embedding-vision）**恒走百炼**（DeepSeek 无视觉模型）。
    复用 `_llm_available()` 会导致：切到 deepseek 后，明明有可用的 DASHSCOPE key 也报
    「百炼未配置」；反之没有 dashscope key 时反而放行、到 SDK 调用处才炸。
    """
    return not settings.mock_external_ai and bool(settings.dashscope_api_key)
```

然后把 `image_caption` / `embed_image` / `embed_text_in_vision` 的守卫换成 `_vision_available()`。
**其余一行不用改**（文本调用继续用 `_llm_available()`，语义正确）。

> 备选（不推荐）：在 `image_caption` 里显式写 `settings.dashscope_api_key` 判断。
> 能修好，但把同一个语义抄三遍，下次再加视觉调用就会漏 —— **抽成一个函数更稳**。


另建议补一个**锁定语义**的用例（防止将来又被"顺手统一"改回去）：

```python
def test_vision_guard_independent_of_text_provider(monkeypatch):
    """切 deepseek 不应影响视觉调用的可用判定（视觉恒走百炼）"""
    monkeypatch.setattr(settings, "mock_external_ai", False)
    monkeypatch.setattr(settings, "llm_provider", "deepseek")
    monkeypatch.setattr(settings, "deepseek_api_key", "sk-deepseek-x")
    monkeypatch.setattr(settings, "dashscope_api_key", "sk-dashscope-y")
    assert dashscope._vision_available() is True          # 有百炼 key 就算可用
    monkeypatch.setattr(settings, "dashscope_api_key", "")
    assert dashscope._vision_available() is False         # 没有就明确不可用
```

## 附：为什么这不是本次合并引入的

- `embed_image` / `embed_text_in_vision` 是我 2026-10-14 加的（R-4），**当时用的是当时正确的守卫**
- `_llm_available()` 是 2026-10-15 被改成按供应商判定的 —— **改的时候没注意到视觉调用也复用它**
- `image_caption` 是你们本来就有的，**它同样受影响** ⇒ 这是**共用的守卫**被改了语义，
  不是某一方写错。两边的调用点都需要跟着换。
