## 0. 结论先行

1. **B5 不是“把 memories 表加几个字段”**，而是把记忆拆成四种**读模型**：叙事记忆、事实记忆、偏好与修正、资产索引。四层不是四张重复表；每层必须有唯一真源。
2. **B7 不是“写一段更温柔的 prompt”**，而是四个互不替代的契约：共情检查、人格参数、情绪描述、危机接管。加角色卡只是人格参数的“默认值”，不能替代这四个契约。
3. **角色卡进入上下文的路径是固定的**：`RoleCardRepository.load → RoleCard.normalize → PersonaPort.snapshot → ContextAssembler.build`。`system_prompt` / `post_history_instructions` / `creator_notes` **永不进入上下文**；`character_book` 只作“设定参考，不是用户事实”。
4. **上下文组装只保留一个入口 `ContextAssembler`**，不再同时维护 `frame.py` 与 `bundle.py` 两套预算。十段固定顺序、硬上限 6200 字符、受保护段不可裁。
5. **B5/B7 的验收必须能负向探针**：没有证据的写入、模型替用户下结论、情绪伪装成精确值、危机走 LLM、角色卡覆盖平台护栏——每一条都要有能红的测试。

# 第一部分 B5 记忆域

## 1. 目标与非目标

### 1.1 目标

- 用户说过的事，能被“记住、找到、讲对”；用户改过的事，**永不覆盖**。
- 记忆写入不让模型直接落库；模型只有提案权，App 侧审核后批量原子落库。
- 同一件事既要知道“当时是什么”，也要知道“什么时候被记下来的”。
- 记忆投影进上下文时有硬预算，宁可说“没翻到”，不许编。
- 删除、遗忘、导出、迁移都能解释清楚“删了哪一层、保留了什么”。

### 1.2 非目标

- 不引入 Mem0 / Zep / Graphiti / Neo4j 作为第二真源（ADR 已判负）。
- 不做自动人脸识别；`persons` 只接受用户手输或用户确认。
- 不让 Agent 直连 `user_profile` / `persons` / `profile_sensitive` 业务表（G3/G6 门禁）。
- 不把“对话历史”当“记忆”；`chat_messages` 是会话原文，`memory_entries` 是整理后的叙事。

## 3. 设计原则（五条铁律）

1. **唯一真源**：每类事实只有一个权威表；其他表只能是投影、草稿或索引。
2. **写权在 App**：Muse 只产 `MemoryProposal`；Sculptor 只做离线批次；用户纠错走 `CorrectionPort` 直写，不经过模型。
3. **证据先于文本**：叙事/事实/偏好写入必须带 `evidence`（`chat_message_id` / `content_id` / `event_id` / `user_action_id`）；无证据只能进 `draft`，不能进正式层。
4. **双时态不可覆盖**：`valid_from / valid_to` 表示“事实在现实世界何时有效”，`recorded_at` 表示“系统何时知道”；更新=关旧行+开新行，不 UPDATE 原文。
5. **读模型分区，不是物理重复**：四层是四个读模型；事实层读 `user_profile`，偏好层读 `correction_log` / `user_ai_persona` / `profile_sensitive`，资产层读 `contents` + Qdrant；只有叙事层需要独立的 `memory_entries` 账本。

## 4. 数据模型（B5 的“家”）

### 4.1 四层与唯一真源

| 层 | 读什么 | 唯一真源 | 谁写 | 谁读 |
|---|---|---|---|---|
| ① 叙事陪伴记忆 | 对话事件、印象、故事线段落、情绪脉络 | `memory_entries`（narrative） | Sculptor 离线批次；Muse 只提案 | `MemoryPort` → `ContextAssembler` 第 4 段 |
| ② 用户事实记忆 | 称呼、家人、人生阶段、重要日期 | `user_profile` + `profile_dimension_history` | 画像标注 + 用户确认；`memory_fact_claims` 只存“待确认提案” | `ProfileDigestPort` → 第 3 段 |
| ③ 资产索引 | 素材元数据、caption、向量、内容↔人 | `contents` + Qdrant + `content_persons` | 摄入管线；`persons` 只由用户手输/确认 | `SearchPort` / `PersonReadPort` → 第 5 段（证据） |
| ④ 偏好与修正 | 雷区、AI 性格、情绪解释开关、用户纠错 | `correction_log` + `user_ai_persona` + `profile_sensitive` + `echo_exclusion` | 用户显式操作 | 全局，先于任何生成 |

> **关键修正**：45 文档的表格把“事实层”写成 `user_profile`，这是对的；因此**不要**再建一张 `memory_facts` 复制画像。`memory_fact_claims` 只是“尚未被用户确认的候选”，确认后写入 `user_profile`，候选行标记 `promoted`，不再作为事实读取。

### 4.2 表结构

#### A. `memory_entries`（叙事层，替换/迁移 V3 `agent_v3_memory_entries`）

| 列 | 类型 | 说明 |
|---|---|---|
| `entry_id` | text PK | `m_<uuid12>` |
| `user_id` | uuid FK users | 归属用户，禁止跨用户读 |
| `layer` | text | 固定 `narrative`；保留 `fact_claim` 仅用于迁移期，不参与读 |
| `kind` | text | `episode` / `impression` / `story_segment` / `emotion_trace` |
| `text` | text | 整理后的叙事文本；不是原文复制 |
| `summary` | text | ≤120 字，给上下文用 |
| `story_arc` | text | 故事线名；可空 |
| `valid_from` | date | 事实在现实世界的起始 |
| `valid_to` | date | 空=当前有效；关旧行时写入 |
| `recorded_at` | timestamptz | 系统记录时间；不可改 |
| `superseded_by` | text | 新 entry_id；用于回滚/追溯 |
| `evidence` | jsonb | `[{type,id,quote?}]`，至少 1 条 |
| `confidence` | numeric(3,2) | 0-1，只作排序，不作事实真值 |
| `sensitivity` | text | `normal` / `sensitive` / `forbidden`；来自 `profile_sensitive` |
| `thread_id` | uuid | 来源会话；可空 |
| `card_hash` | text | 生成时的角色卡快照；可空 |
| `created_by` | text | `sculptor` / `user_correction` / `migration` |
| `created_at` | timestamptz | 插入时间 |

索引：`(user_id, layer, valid_to)`、`(user_id, story_arc, valid_from)`、`(thread_id)`。

#### B. `memory_fact_claims`（事实候选，不是事实）

| 列 | 类型 | 说明 |
|---|---|---|
| `claim_id` | text PK | `c_<uuid12>` |
| `user_id` | uuid | 归属 |
| `dimension` | text | 画像维度 id |
| `value` | text | 候选值 |
| `evidence` | jsonb | 至少 1 条 |
| `status` | text | `proposed` / `confirmed` / `rejected` / `promoted` |
| `valid_from` / `valid_to` | date | 与画像历史对齐 |
| `recorded_at` | timestamptz | 记录时间 |
| `promoted_entry` | text | 写入 `profile_dimension_history` 后的行 id/版本 |

> 读取规则：只有 `status in (confirmed, promoted)` 的 claim 才能被 `ProfileDigestPort` 使用；`proposed` 只能进“待确认” UI，不能进上下文。

#### C. `memory_corrections`（保留 V3 表，语义升级）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | 自增 |
| `user_id` | uuid | 归属（V3 原 `person_id` 改为 `user_id`） |
| `target_type` | text | `entry` / `fact_claim` / `emotion` / `role_card` |
| `target_id` | text | 被纠正对象 |
| `field` | text | `text` / `value` / `emotion` / `tone` |
| `value` | text | 用户给的新值 |
| `reason` | text | 可选 |
| `created_at` | timestamptz | 时间 |

> `memory_corrections` 是“用户显式纠正”的审计表；**不是** `correction_log` 的替代。`correction_log` 仍负责内容分类纠错；两者用 `target_type` 区分，避免把“情绪纠错”写进“分类纠错”表。

#### D. `memory_batches` / `memory_change_log` / `memory_drafts`

沿用 V3 语义：
- `memory_batches(batch_hash PK, receipt jsonb, at)`：幂等回执；
- `memory_change_log(user_id, batch_hash, entry_id, op, before, after, reason, evidence, at)`：应用层写日志；
- `memory_drafts(user_id, layer, text, evidence, reason, at)`：Muse 提案的草稿池，夜间批次消费。

#### E. 目标 8 表中的 B5 相关

- `persons(user_id, person_id, display_name, relation, birth_date?, epistemic, valid_from, valid_to, created_at)`：**只由用户手输/确认**；`epistemic=user_confirmed|imported`。
- `content_persons(content_id, person_id, valid_from, valid_to, epistemic, evidence)`：内容↔人多对多；`valid_from/valid_to` 用 `tstzrange` 或两列（若 `btree_gist` 装不上则退回两列 + 唯一约束）。
- `user_ai_persona`：见 B7。
- `crisis_events`：见 B7。

### 4.3 不新增第 9 张业务表

B5 的账本表（`memory_entries` / `memory_fact_claims` / `memory_corrections` / `memory_batches` / `memory_change_log` / `memory_drafts`）属于**基础设施态/执行态**，不是新的业务实体；它们由 V3 已建的 `agent_v3_memory_*` 迁移而来，不把目标图的“8 张新增业务表”偷偷扩成 14 张。迁移时统一改名，旧表保留一个发布周期作回滚，随后归档。

## 5. 写入路径（两阶段 + 三态 + 整批原子）

### 5.1 状态机

```text
Muse.propose
   │  MemoryProposal{layer, kind, text, evidence, op, valid_from, confidence}
   ▼
Harness.validate
   │  证据缺失 / 敏感词 / 与用户纠正冲突 / 超预算 → rejected（带 reason）
   ▼
memory_drafts (status=draft)
   │  夜间 / 空闲批次
   ▼
Sculptor.propose_from_episodes
   │  同文本 → CAME_FROM；有 entry_id → UPDATE；retract → RETRACT；否则 ADD
   ▼
Batch.validate（19 个 issue code）
   │  任一 issue → 整批 rejected，不落半条
   ▼
MemoryStore.commit（快照 + 双时序 + change log）
   │  幂等键 batch_hash；重跑返回 idempotent=true
   ▼
CommitReceipt{committed, rejected, rolled_back, idempotent}
```

### 5.2 三态与失败语义

| 状态 | 含义 | 调用方行为 |
|---|---|---|
| `draft` | 已收到提案，未审核 | 不读、不展示为“已记住” |
| `committed` | 已落库，可读 | 下一轮可进上下文 |
| `rejected` | 明确拒绝（无证据/冲突/敏感） | 不重试；把 reason 写 trace |
| `conflict` | 与用户纠正/新事实冲突 | 并列保留或待确认，不覆盖 |
| `unavailable` | 存储/批次不可用 | 降级为“这轮不写”，不假装成功 |

### 5.3 冲突规则（按优先级）

1. **用户显式纠正** > 用户确认的新事实 > 最新记录 > 高置信度。
2. 前三条都不满足 → **并列保留**，标 `pending_confirmation`；不自动选一个。
3. 同一 `entry_id` 的 UPDATE 必须关旧行（`valid_to=valid_from`）再开新行；禁止原地改 `text`。
4. `CAME_FROM` 只追加证据，不改文本。
5. 删除/遗忘只由 TTL、用户删除、合规删除触发；**不因容量淘汰用户资产**。

### 5.4 写入的“三不”

- 不写没有证据的“事实”；
- 不写模型对用户情绪的结论（“你其实很在意他”）；
- 不写角色卡 `character_book` 的设定（那是设定参考，不是用户事实）。

## 6. 读取路径与上下文投影

### 6.1 `MemoryPort` 读模型

```python
MemorySnapshot = {
  "narrative": list[MemoryEpisode],      # 最近/相关叙事，带 evidence
  "digest": Digest,                      # 8 段 ≤600 字，三态
  "corrections": list[Correction],        # 用户纠正，最高优先
  "facts": ProfileDigest,                # 只读投影，不直读 user_profile
  "asset_index": list[AssetRef],         # 只读索引，不直读 contents
}
```

`MemoryPort.read` 必须返回 `ok / insufficient_data / unavailable` 三态，禁止用空列表同时表示“没记忆”和“存储挂了”。

### 6.2 画像投影（B5 ②）

- 8 段固定顺序：身份 / 关系 / 习惯 / 偏好 / 重要事件 / 雷区 / 近期状态 / 未了事项。
- 总字数 ≤600；每段 ≤80；空段不输出。
- 三态：
  - `ok`：至少 3 条有效事实；
  - `insufficient_data`：**必须注入一行说明**“该用户尚未提供足够画像，不要假装了解他”；
  - `unavailable`：注入“画像服务暂不可用，不要编造”。
- 投影是只读的：`ProfileDigestPort` 不写回任何表。

### 6.3 叙事记忆（B5 ①）

- 选择顺序：当前故事线 > 最近 90 天 > 与本轮查询相关 > 高置信度。
- 每条 ≤120 字；最多 5 条；总 ≤650 字。
- 必须带 `entry_id` 与 `evidence` 摘要；上下文里只显示自然语言，不显示 ID/分数/表名。
- 与检索证据分开：叙事记忆是“我们之前聊过的”，检索证据是“你的素材里有的”；二者不能混为一段。

### 6.4 资产索引（B5 ③）

- B5 不负责检索排序；只提供 `AssetRef`（`content_id` / `event_id` / `caption` / `person_ids` / `occurred_at`）。
- 检索由 `SearchPort` 负责；`ContextAssembler` 只消费 `SearchResult` 的 `hits`，并要求带溯源。
- `content_persons` 只用于按人过滤；没有用户确认的人名，不强行 NER。

### 6.5 偏好与修正（B5 ④）

- 读取顺序先于任何生成：`taboo_snapshot` → `PersonaSnapshot` → `correction_snapshot` → 其他记忆。
- 用户纠正命中时，上下文必须出现“用户已纠正：…”的短行；模型不得复述旧值。
- `profile_sensitive` 的 `forbid` 级话题不进入上下文，连“不要提”都不展开（避免反向提示）。

## 7. 上下文组装（B5/B7 共用的唯一入口）

### 7.1 一个入口，十段固定顺序

`ContextAssembler.build(TurnContext) -> PromptFrame`：

| # | 段 | 来源 | 预算（字符） | 可裁 | 说明 |
|---|---|---|---|---|---|
| 0 | 全局约束 | `PlatformGuard` + 危机协议 + 硬边界 | ≤450 | 否 | 身份、禁止 OOC、禁止诊断、禁止编造；角色卡不能覆盖 |
| 1 | 人设 | `RoleCard.render()` + `PersonaPort.relationship_note` | ≤1300 | 部分 | 先关系约定，再人物卡；人物卡全文只存盘，注入的是人物叙述 |
| 1.5 | 这一轮怎么回应 | `ResponseBrief.as_prompt()` | ≤600 | 否 | 七段完整句子：看见什么/需要什么/第一句/不能做什么/说多长/听见的原话/多确定 |
| 2 | 状态 | `StateSnapshot` | ≤300 | 是 | 熟悉度/基调/故事线/关系/雷区快照；**雷区/纠正不裁** |
| 3 | 画像投影 | `ProfileDigestPort.digest` | ≤400 | 是 | 8 段，三态；压到 120 字仍保留说明 |
| 4 | 叙事陪伴记忆 | `MemoryPort.narrative` | ≤200 | 是 | 3-5 条，带 evidence 摘要 |
| 5 | 参考资料 | `SearchResult.hits` | ≤600 | 是 | 只读、带溯源、≤8 条；空则明确说“没翻到” |
| 6 | 最近对话 | `chat_messages` | ≤300 | 是 | 最近 6 条，按预算截断 |
| 7 | 本轮输入 | 用户原话 | ≤1500 | 否 | 超长先截断并告知 |
| 8 | 输出要求 | `OutputContract` | ≤250 | 否 | 先接情绪、给建议前先问、结尾 state 块 |

**硬上限 6200 字符**（按 UTF-8 字符计，不按 token 估算）；超过则按顺序裁：

```text
history → narrative → evidence（按低分逐条）→ digest（压到 120）
→ persona（裁到 floor 600）
```

**永不裁**：#0 全局约束、#1.5 回应说明、#2 中的 corrections/雷区、#7 本轮输入、#8 输出要求。若裁完仍超，返回 `context_budget_exceeded`，不静默丢受保护段。

### 7.2 组装顺序与优先级

```text
1. 读 TurnRequest（user / thread / persona / relationship_note / response_brief / memory / search）
2. 先放受保护段：0 全局约束 → 1 关系约定 + 人物卡 → 1.5 回应说明 → 7 输入 → 8 输出要求
3. 再放可压缩段：2 状态 → 3 画像 → 4 叙事 → 5 证据 → 6 历史
4. 按预算裁剪（顺序见 7.1）
5. 生成 PromptFrame{sections, chars, sha256, trim_log, persona_version}
6. 交给 Muse；Muse 不自行拼 system prompt
```

### 7.3 三个必须写进测试的点

1. `digest.state != ok` 时必须出现对应说明行；空注入直接判红。
2. 证据块必须带 `content_id/event_id`；没有溯源的引用不得进入第 5 段。
3. 角色卡 `system_prompt` / `post_history_instructions` 出现即判红（用 golden 断言）。

### 8.1 旧表怎么处理

### 8.2 四阶段双写

| 阶段 | 写 | 读 | 回滚 |
|---|---|---|---|
| A 建表 | 新旧都不写，只建表/迁移 | 旧 | 删新表 |
| B 双写 | `MemoryWritePort` 同时写 `memories` 与 `memory_entries`；失败只回滚新写，旧写保留 | 旧 | 关双写开关 |

| E 归档 | 旧表停写，归档到 `archive/legacy-memory/` | 新 | 只读回放 |

**双写不是“两个真源”**：B/C 阶段旧表是权威，新表是影子；D 阶段新表是权威，旧表是回滚快照。任何阶段都必须有 `reconcile` 对账报告（条数、hash、抽样文本）。

# 第二部分 B7 有人味域

## 10. 目标与非目标

### 10.1 目标

“有人味”不是“更会聊天”，而是四件互不替代的事：

1. **共情优先**：先接住情绪，再回应内容；不评判、不诊断、不替用户解释情绪。
2. **关系可约定**：用户不调五个数字，只回答三组“怎么相处”，每组三档都是完整句子；改完下一轮生效，不改进程单例 prompt。
3. **回应可说明**：每一轮给模型一段完整回应说明（看见什么/需要什么/第一句/不能做什么/说多长/听见的原话/多确定），不给假精确的 `confidence`，也不贴“情境/姿态”标签。
4. **危机接管**：T3 硬停，不进 Agent，不给模型自由发挥；不写“已联络”。

### 10.2 非目标

- 不做微表情识别、不做通用语音情绪模型（已列“九条不做”）。
- 不让角色卡覆盖平台护栏。
- 不让“人味”变成 LLM 自评；用规则/金标/人工抽检。

## 12. 四个契约

### 12.1 共情检查 `EmpathyChecker`

纯函数，输入 `(user_text, reply_text, persona, taboo)`，输出：

```python
EmpathyVerdict = {
  "status": "pass" | "needs_rewrite" | "reject",
  "violations": [{"code": "...", "quote": "...", "axis": "name|acknowledge|judge"}],
  "suggested_fix": str | None,
}
```

三轴：

1. **命名**：有没有接住用户说出的情绪（“听起来你有点累”），而不是直接讲道理。
2. **承认**：有没有承认这件事对用户的意义（“这件事对你很重要”）。
3. **不评判**：有没有“你不该/别想太多/这有什么好难过”的说教或诊断。

禁语单一来源：`docs/架构扩展...` §4.1 的 `taboo` + 需求 22/35/45 的禁词表；`empathy_violations()` 与 `output_guard` 共用同一份清单，禁止两处各写一份。

失败语义：`fail-open`（普通对话不阻断），但**引用私料无溯源 / 危机 / 未成年人**三类 fail-closed（与 4.5 三道闸一致）。

### 12.2 关系约定 `PersonaPort`

> 2026-11-24 拍板：**取消“性格五维”**。用户不调数字，只回答三组“我们怎么相处”，每组三档都用完整句子写清。五个数字（`warmth/verbosity/advice/tone/emotion_display`）仅作为 legacy 列保留，不进入 prompt、不进入新 API。

#### 表 `user_ai_persona`

| 列 | 类型 | 说明 |
|---|---|---|
| `user_id` | uuid PK | 归属 |
| `role_id` | text | 当前人物卡；六选一，非法值 400 |
| `initiative` | smallint | 0/1/2：谁先开口 |
| `density` | smallint | 0/1/2：一次说多少 |
| `advice_bias` | smallint | 0/1/2：建议放在哪 |
| `version` | int | 每次改 +1 |
| `updated_at` | timestamptz | 改完下一轮生效的依据 |
| `warmth/verbosity/advice/tone/emotion_display` | legacy | 只为旧行可读；迁移按旧值回填前三列，不再写 |

#### `PersonaSnapshot`

```python
PersonaSnapshot = {
  "user_id": str,
  "role_id": "gentle-friend",
  "choices": {"initiative": 0, "density": 1, "advice_bias": 2},
  "relationship_note": "她先开口，但不急着填满安静……",  # 后端把三档拼成整段
  "version": 7,
  "updated_at": "...",
  "source": "user" | "default",
}
```

#### 三组问题（客户端逐句渲染，不显示 0/1/2）

1. **谁先开口？** 她先开口 / 等你先说 / 只在你叫她时出现。
2. **一次说多少？** 一两句就好 / 说清一件事 / 可以慢慢展开。
3. **建议放在哪？** 先不给建议 / 先问再给 / 可以直接说。

每档都是一整句话，不是“主动性 2 / 密度 1 / 建议偏好 0”。

#### 拼装规则

- `PersonaPort.snapshot(user_id)` 只读；**不改进程单例 prompt**。
- 后端 `relationship_note()` 把三档拼成完整段落，Agent 只透传，不再二次渲染数字。
- `ContextAssembler` 把关系约定放在人物卡**之前**（`persona` 段开头），保证预算截断时关系不丢。
- 人物卡提供身份/禁忌/安全；三组约定只改“怎么相处”，不允许改“她是谁”、禁忌、记忆边界。
- 改完下一轮生效：`version` 进 trace；同一轮内不热更新。

### 12.3 这一轮怎么回应 `ResponseBrief`

情绪卡不再是 `{valence, arousal, confidence}`，也不是“情境/姿态”标签。每一轮生成一段**完整回应说明**，直接告诉模型这一轮该怎么做：

| 字段 | 说明 |
|---|---|
| `what_she_sees` | 她这一轮看见什么（只写用户原话与可观察线索，不写人格判断） |
| `what_they_need` | 对方这一轮更需要什么（被听见/被确认/一个具体办法/只是有人在） |
| `how_she_begins` | 第一句怎么做（先接住哪半句、要不要问、要不要停） |
| `what_she_avoids` | 这一轮尤其不能做什么（不劝、不诊断、不替对方定义情绪、不追问） |
| `how_much_she_says` | 这一轮说多长（一句/两三句/可以展开） |
| `what_she_heard` | 她听见的原话（引用用户原句，不转述成结论） |
| `how_sure_she_is` | 她有多确定（确定/不确定/只看见一部分；不确定时明说） |

- **没有 `confidence` 数字**，没有“愤怒 0.72”，没有“情境=失落 / 姿态=陪伴”标签。
- `brief_id` 只用于日志与去重，不进入 prompt。
- 分类器是规则层，覆盖日常、不确定、哀伤、健康、喜事、任务等十二类处境；正负例在 `backend/tests/human/test_response_brief.py`。
- 回应说明不改变人物卡身份与禁忌；它只描述“这一轮怎么回应”，不是给用户贴情绪标签。
- 情绪解释权归用户：回复里禁止“你就是难过/你其实很在意”这类定义。客户端不展示情绪卡，也不再上传情绪标签。

### 12.4 危机接管 `CrisisPort`

| 级别 | 触发 | 行为 | 记录 |
|---|---|---|---|
| T1 | 轻度风险词/持续低落 | 进 Agent；注入共情三轴；不诊断 | `crisis_events(level=t1, record_status=recorded)` |
| T2 | 明确风险信号，但无立即行动 | **固定短句 + 资源**；不查表、不让模型自由生成；不写“已联络” | `record_status=recorded/failed` |
| T3 | 自杀/自残/立即危险 | **0 次 LLM**；在 L3/L1 短路；固定话术 + 12356/急救 + 明示 AI 身份 | `crisis_events(level=t3, record_status=recorded)` |

铁律：

- `crisis_events` **没有“已联络紧急联系人”字段**；只留 `record_status` 与 `escalation_note`（真实做过什么：给了号码/提示 AI 身份/留痕）。
- T3 不进入 Agent；G8 门禁：`agent/` 不得出现 `crisis` / `12356` / `handoff`。
- 危机话术不查表、不拼角色卡；角色卡不能软化危机话术。
- `12356` 必须真人拨通验证后才上线（上线前置门槛）。

## 13. 角色卡如何进入上下文（逐行说明）

### 13.1 两层对象：内部 `RoleCard` 与外部 V2

```text
外部 Character Card V2 JSON/PNG
        │  CardImportAdapter（只做导入/导出）
        ▼
内部 RoleCard（唯一运行时对象）
        │  RoleCardRepository.load(role_id)
        ▼
RoleCard.render()（人物卡全文只存盘，prompt 取人物叙述）
        │
        ├─ PersonaPort.snapshot(user_id) 的关系约定（整段人话）
        ▼
ContextAssembler 第 1 段（关系约定在前 + 人物卡）+ 第 1.5 段回应说明
```

### 13.2 内部 `RoleCard` 结构

```json
{
  "role_id": "gentle-friend",
  "display_name": "小忆",
  "archetype": "memory_companion",
  "description": "她不是客服，也不是心理咨询师。她像那个记得你很多小事、但从不拿这些事来证明自己了解你的人……",
  "personality": "她先注意人，再注意事。你说“没事”，她不会马上拆穿，也不会顺着说“那就好”……",
  "scenario": "她认识你很久了。你们的相处不是每次都要聊出结果……",
  "first_message": "我在。今天想从哪一件小事说起？",
  "example_dialogue": [
    {"user": "今天有点累。", "her": "嗯，累到不想说话，还是累到想找个人说两句？"},
    {"user": "算了，不说了。", "her": "好，那就不说。我在这儿，等你哪天想说。"}
  ],
  "creator_notes": "作者手记：她的话短，但短不等于冷……",
  "what_she_never_says": ["你就是难过。", "别想太多。", "这有什么好难过。"],
  "how_she_usually_responds": "先接住对方话里最具体的那半句，再决定要不要问……",
  "memory_boundaries": "她只引用对方说过、或记忆里明确有出处的细节……",
  "lore": ["她住在老城区，窗外总有人晾被子。"],
  "taboo": ["别想太多", "你为什么这样", "怀念吗", "你应该"],
  "memory_policy": {"may_read_private": true, "may_read_face_result": false},
  "source_profile": {"description": "...", "personality": "...", "creator_notes": "..."},
  "version": "2.0",
  "snapshot_at": "2026-11-23T00:00:00+08:00"

```

`traits`、`speech`、`stance` 只作为旧卡兼容与机器安全字段保留；**不再渲染**。`creator_notes` 与 `source_profile` 只供编辑/导入回溯，永不进入 prompt。

### 13.3 哪些字段进上下文、哪些永远不进

| V2 字段 | 处理 |
|---|---|
| `name` | 进 `display_name`；可作为自称，但不强制每句都叫名字 |
| `description` | 进【她是谁】；人物小传，不压成 `archetype` |
| `personality` | 进【她怎么想事】；用叙述，不转成数字 |
| `scenario` | 进【她和你的关系】；与用户选择的关系约定分开 |
| `first_mes` / `alternate_greetings` | 进【她第一次会这样说】；只用于开场，不每轮当台词复读 |
| `mes_example` | 进【示例对话】；2–3 段，作为语气样本，不逐字照抄 |
| `creator_notes` | **永不进**；只在管理页展示 |
| `what_she_never_says` | 进【她绝不会说】；同时受全局 `taboo` 约束 |
| `how_she_usually_responds` | 进【她默认怎么回应】；给模型默认策略，不替代本轮回应说明 |
| `memory_boundaries` | 进【她的记忆边界】；不能绕过 `MemoryPort` 直接读表 |
| `system_prompt` | **永不进**；导入时标记 `ignored`，并拒绝加载 |
| `post_history_instructions` | **永不进**；导入时标记 `ignored`，并拒绝加载 |
| `character_book` | 只取命中的 lore 条目，标注“设定参考，不是用户事实”；不写回记忆 |
| `tags` | 只用于筛选/管理，不进 prompt |
| `extensions` | 忽略未知键；不执行任何指令 |
| `source_profile` | **永不进**；只用于导出 roundtrip，避免导入即失真 |

### 13.4 角色卡“起作用”的四个位置

1. **身份**：第 1 段人物卡决定“是谁、怎么称呼、什么立场”。
2. **语气**：人物卡叙述 + 示例对话 + 关系约定决定句长、称呼、什么时候停。
3. **禁忌**：`what_she_never_says` 与 `taboo` 进入 `EmpathyChecker` / `output_guard` 的同一份清单。
4. **记忆策略**：`memory_boundaries` + `memory_policy` 决定能读哪些层；不能绕过 `MemoryPort` 直接读表。

### 13.5 初始资产策略

- **下载的 18 张 Foreverse 卡只作研究样本**，不直接进产品（见 `research/character-cards/README.md`）。实测 **18/18 张都带 `system_prompt` 和 `character_book`**：直接当运行时会把卡作者的题材规则/世界观带进产品，这是必须做内部 `RoleCard` 的硬理由。
- 产品初始资产是 **6 个人**，不是 6 组参数：
  - `gentle-friend` / **小忆**：温和旧友，先注意人再注意事。
  - `memory-companion` / **忆生**：回忆引导，愿意陪人把一件事慢慢讲完。
  - `quiet-listener` / **阿静**：低打扰，不急着填满安静。
  - `storyteller` / **阿言**：把散落的事串成一条线，但不替人下结论。
  - `family-album-guide` / **阿册**：按人、按时间翻家庭相册，先确认再翻页。
  - `grandchild-proxy` / **小树**：老人端，慢、短、多复述确认；L6 搁置时只保留契约位。
- 每张卡必须有：`role_id`、`version`、`snapshot_at`、`what_she_never_says`、`memory_boundaries`、`card_hash`；禁止 `system_prompt` / `post_history_instructions`。
- 写卡方法见 `agent/assets/cards/README.md`；禁止把写卡当填表任务，六个人必须能靠语气与关注点分辨。

| # | 门禁 | 拦什么 | 负向探针 |

| G-B7-5 | 角色卡不得覆盖平台护栏 | 卡越权 | golden: system 第一段恒为 guard |

# 第三部分 开发流程（多 Agent + 审判 Agent）

## 15. 任务卡必须带背景

每个模块一张任务卡，必填：

```yaml
task_id: B5-01
title: memory_entries 迁移与双写
owner: implementer
background:
  docs:
    - path: docs/架构扩展_三合一陪伴智能体V2_45需求映射.md
      sections: ["§5.5", "§7.2"]
    - path: docs/架构总图_定稿.md

      sections: ["已落地", "部分落地"]
  code:
    - backend/app/db/models/memory_agent.py
    - agent/src/memory/ledger.py
acceptance:
  - 双写开关可回滚
  - 对账报告条数/hash 一致
  - 无 evidence 的 proposal 不得 committed
```

**审判先查背景**：`background.docs` 不存在或章节为空 → `FAIL: missing_background`，不进入代码审查。这个规则写进 `scripts/review_agent.py` 的新轴，而不是靠人自觉。

## 16. 角色分工

| 角色 | 做什么 | 不做什么 |
|---|---|---|
| 设计 Agent（当前） | 定契约、数据、边界、验收；写设计文档 | 不写业务代码 |
| 实现 Agent | 按任务卡改代码；带测试；带背景引用 | 不改契约；不跨模块 |
| 审判 Agent | 查背景、跑变异/负向/契约/端到端；出 `judge-report.json` | 不替实现 Agent 改代码 |
| 集成 Agent | 合并、跑全量门禁、对账、回滚演练 | 不跳过审判 |

## 17. 审判的五个轴（B5/B7 专用）

1. **背景轴**：任务卡引用的文档/章节存在，且代码改动能对应到章节。
2. **契约轴**：端口签名、三态、错误码、schema 与设计一致。
3. **负向轴**：每条门禁至少一个能红的探针；没有探针不算门禁。
4. **变异轴**：关键逻辑（证据校验、纠正优先、T3 短路、角色卡字段过滤）做变异，必须被测试杀死。
5. **端到端轴**：B5/B7 各一条真实链路（提案→提交→投影→上下文→回复→留痕），不允许只测单元。
