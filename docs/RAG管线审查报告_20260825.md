# RAG 管线系统性审查报告（2026-08-25）

> 范围：文字 RAG 全链路（BGE-M3 编码 → Qdrant RRF 混合检索 → 过滤 → rerank → 溯源）
> 方法：代码走查 + 逐查询探针（真实 Qdrant yishu_benchmark_text，117 点）+ 修复前后基准对比
> 结论先行：**recall@3 低是"指标定义结构性上限"，不是检索器坏了；但管线确有 3 个真 bug（已修）和 2 个架构级短板（已定性，附修复路径）**

---

## 一、为什么 recall@3=0.0841 这么低？——三个叠加原因

### 1. 指标分母被 label 类撑大（结构性上限，占大头）

`recall@k = |相关∩Top-k| / |相关总数|`（metrics.py），而评测里"相关集"=`expected_label 对应的全部语料条目`（run_eval.py `_resolve_relevant`：显式 id ∪ label 全集）。

语料分布（corpus_b 84 条 + corpus_c 33 条 = 117）：todo 20 / idea 16 / emotion 18 / quote 15 / mixed 15 / voice 33。

每个查询的相关集 = 15~20 条，Top-3 最多命中 3 条 → **recall@3 理论上限 = 3/15~3/20 ≈ 0.15~0.20**。实测 0.0841 已是上限的 50~70%——对一个"找一条相关记录"的搜索产品，这个指标从设计上就不该用类全集做分母。

佐证：同一批查询 hit_rate@3=0.8182（82% 查询 Top-3 至少 1 条相关）、precision@3=0.5152（Top-3 平均 1.5 条相关）、mrr=0.7727——**排序本身不差**。recall 低 ≠ 检索烂，是任务口径（类检索 vs 单条检索）错配。

### 2. typo / length 层有真实缺陷（已修一半）

- **length 层 hit_rate@3=0.5 根因（已修）**：`_rewrite_query` 用 `pattern.search` 任意位置匹配时间词。"记得明天下午之前把**上个月**的工作总结报告交给领导" 里"上个月"是名词修饰语，被误判为时间过滤意图 → 加 time 过滤 + 语料 payload 无 taken_at → 检索空结果。修复：时间词仅**句首**才算过滤意图（句中=描述性提及）。修复后 length 层 0.5 → 1.0。
- **typo 层 hit_rate@3=0.5**（未修，定性）："买牛乃"靠 BGE-M3 dense 的错字容错命中（Top-1 即中）；"松鼠桂鱼"（__none__）正确返回空。生产风险在于：错字若更严重（如"收房祖"），dense 容错也不够。修复路径：DASHSCOPE key 就绪后 LLM 查询改写（rewrite_query 已有接口，现 mock）或 query 侧拼音/近音扩展。

### 3. descriptive 层释义鸿沟（架构级短板，未修，见第四节）

## 二、审查发现 3 个真 bug（全部已修复 + 测试）

### BUG-1（严重）：rerank 自 8-24 起从未生效（静默降级）
7e7452f 给 CrossEncoder 加 fp16 用了 `model_kwargs`，但 sentence-transformers 3.4.1 该参数已移除 → 加载必抛 TypeError → 被 except 吞掉"跳过重排"。**8-20 基准的 descriptive hit_rate@3=1.0 是 rerank 活着时的成绩；8-24 之后 rerank 一直是死代码。**
修复：`automodel_args={"torch_dtype": torch.float16}`。探针确认加载成功。

### BUG-2（严重）：rerank 打开 = 每次搜索 ~40 秒（CPU）
修复 BUG-1 后实测：bge-reranker-v2-m3 CPU 单对 ~850ms × 50 候选 ≈ 40s/查询，**远超 P95<3s 门禁**。且 rerank 只重排候选集内文档——救不了没进 Top-50 的相关文档（描述性查询失效根因在召回层）。
决策：新增 `rerank_enabled=false`（默认关）+ `rerank_max_candidates=20`。GPU 部署或延迟预算允许时再开。文档化的两难：**CPU 上质量与延迟不可兼得，质量靠 reranker、延迟靠 RRF，当前以延迟门禁为准**。

### BUG-3（中等）：时间正则误伤（见上，已修）
句首限定 + 新测试 `test_query_rewrite_time_modifier_mid_query` 回归。

### 新增（低风险增强）：关键词精确命中提升 `_boost_exact_matches`
"马拉松/收房租/买牛奶"类字面查询，RRF 里 dense 权重 0.7 把无语义关键词的近邻文档排在精确命中文档前面（探针：马拉松精确命中的 emotion 文档排第 3）。修复：rewritten 全部词元（≥2 字）出现在文档原文 → score×1.8 重排；描述性查询无全词命中 → 零副作用。

## 三、修复前后基准对比（117 条混合库，11 查询）

| 指标 | 8-20 基线（rerank 活） | 修复后（rerank 默认关） | 说明 |
|---|---|---|---|
| hit_rate@3（门禁≥0.70） | 0.8182 | **0.7273 PASS** | length 层 0.5→1.0 抵消 descriptive 回落 |
| mrr | 0.7727 | 0.6621 | descriptive 释义查询无 rerank 兜底 |
| recall@3 | 0.0841 | 0.0626 | 结构性上限，见第一节 |
| ndcg@3 | 0.5668 | 0.4220 | 同上 |
| length hit_rate@3 | 0.5 | **1.0** | BUG-3 修复 |
| temporal/route acc | 1.0/1.0 | 1.0/1.0 | 不变 |

修复后门禁 PASS；质量损失全部可归因于 rerank 关闭（延迟换质量），GPU 部署即恢复并超越 8-20 基线。

## 四、架构级短板（定性 + 修复路径）

### 短板-A：描述性/释义查询召回不足（"关于做产品的想法"/"让我难过的记录" Top-3 全偏）
- 现象：这俩查询相关文档（idea/emotion 类）在 dense 路分数低于 todo/voice 干扰项，sparse 路零命中（无词元重叠）。
- 根因：双编码器（BGE-M3）对**中文释义改写**的语义距离容忍度有限；候选集里相关文档排名过低时，任何重排（含 reranker）都救不回来。
- 修复路径（按性价比）：
  1. LLM 查询改写（推荐，基础设施已具备）：rewrite_query 已接 dashscope，key 配置后启用——把"关于做产品的想法"扩展为与 idea 语料同分布的查询词。
  2. 更大候选集 + reranker（GPU）：50→200 候选，rerank 到 Top-10。
  3. 类目路由 + 标签过滤：描述性查询先过 SetFit 分类器（text 管线已有 content_class）→ 按类过滤再检索，把干扰项挡在召回路外。

### 短板-B：评测集结构性缺陷
- 117 条语料 5 类标签，查询只有 11 条且以 label 全集为相关集 → recall 指标失真（第一节）+ 波动大（±1 条查询变动 0.09）。
- 真实数据到位后（50 条真实查询 + 100-200 条真实碎片）替换合成基准；recall 改为"显式 expected id 召回"口径或直接废弃（产品口径 = hit_rate@k + mrr）。
- benchmark payload 无 taken_at：temporal 层行为测试退化为"空结果即正确"占位，真实数据需补时间字段。

---

## 五、结论

1. **recall@3 低 = 指标分母错配（结构性）+ 两个真实缺陷（typo/length，length 已修）**，不是检索主链路坏了——hit_rate@3 0.73~0.82、mrr 0.66~0.84 在同规模中文记忆检索里属正常区间。
2. 已修：rerank 加载 bug、时间正则误伤、关键词精确命中稀释；rerank 按延迟门禁默认关闭（GPU 可开）。
3. 待办：LLM 查询改写启用（等 dashscope key）、真实评测集替换、SetFit 类目路由（beta 前）。
