# RAG 索引可靠性设计（2026-11-25）

> **范围**：`pipeline._index_after_commit` 之后的 Qdrant 索引可靠性。
> **现状**：主提交后写 Qdrant；失败只 `logger.warning`，没有 outbox、重试、状态查询或告警。
> **目标**：让「记录已 done、但向量没写进去」可重试、可查询、可告警；不改变 DB 是内容真值的口径。
> **非目标**：不把向量写入提前到 DB commit 之前；不做跨库原子事务；不承诺「记录后 5 秒可搜」为 SLA。

---

## 一、现状与证据

| 项 | 现状 | 位置 |
|---|---|---|
| 写入时机 | DB 主提交之后 | `backend/app/services/pipeline.py::_index_after_commit`（`process_content` 调用） |
| 失败处理 | `logger.warning("后置索引失败 content=%s: %s", ...)`，不回滚、不重试 | `pipeline.py` 调用处 |
| 幂等 | `point_id_for(content_id)` UUID5 + 整点 upsert，重跑安全 | `vector_store.upsert_content` |
| 空文本 | 跳过索引并记 INFO（照片 caption 失败等） | `_index_content` |
| 兜底 | Qdrant 异常/空召回走 PG 精确/全文兜底 | `rag/pg_fallback.py`、`_pg_exact_search` |

**问题**：失败只留一行日志，没有「这条内容现在能不能被搜到」的可查询状态；RQ 重投/超龄重扫可以重跑，但依赖人工发现。PG 兜底能缓解空召回，但替代不了向量检索。

---

## 二、推荐方案：contents 状态列 + RQ 持久化重试

### 2.1 数据模型（一次迁移）

在 `contents` 增加（均可空，避免回填阻塞）：

| 列 | 类型 | 含义 |
|---|---|---|
| `index_status` | varchar(16) | `pending` / `indexing` / `indexed` / `failed` / `skipped` |
| `index_error` | text | 最后一次失败原因（截断，不含正文） |
| `index_retry_count` | int default 0 | 已重试次数 |
| `index_last_retry_at` | timestamptz | 最后一次重试时间 |

> 备选：独立 outbox 表（`index_outbox`）。contents 列更简单，且状态与内容同生命周期；如果后续要多种索引目标（文本/图片/未来视觉塔），再拆 outbox。

### 2.2 写入流程

```
DB commit (status=done)
  → index_status=pending
  → 投递 RQ 任务 index_content(content_id, target="text+image")
  → worker: index_status=indexing
      → 成功: indexed
      → 失败: failed + index_error + retry_count++；RQ 按退避重试
  → 超过重试上限: 保持 failed，等日任务/人工重投
```

- **幂等**：沿用 UUID5 点 id + upsert；重复任务不产生重复点。
- **修改/删除**：现有更新/删除链路继续同步 Qdrant；状态列只描述「最近一次索引」。
- **超时**：worker 任务加硬超时，避免大文件卡死队列。
- **空文本**：`skipped`，并在管理/评测侧可见（不是 `indexed`）。

### 2.3 查询与告警

- 管理/运维查询：`select index_status, count(*) from contents group by 1;`
- 失败样例：`select id, index_retry_count, index_error from contents where index_status='failed' limit 20;`
- 告警：failed 数 > 阈值（如 10）或 24h 新增 failed > 0；日志/监控按现有体系接。
- 评测/真机：搜索不到时先看 `index_status`，区分「索引没写」与「召回没中」。

### 2.4 故障注入验收

1. 停 Qdrant → 写入一条内容 → 确认 DB `done`、`index_status=failed`、`index_error` 非空；
2. 恢复 Qdrant → 触发重试/日任务 → 确认 `indexed`，且搜索能命中；
3. 重复投递同一任务 → 确认不产生重复点；
4. 统计恢复时间与丢失数；把「记录后 N 秒可搜」作为观察值，不写成承诺。

## 三、实施顺序（建议）

| 步 | 内容 | 验证 |
|---|---|---|
| 1 | 迁移 + ORM 字段（可空） | `alembic upgrade head`；`alembic check` 无漂移 |
| 2 | `_index_after_commit` 写状态 + 投递 RQ；worker 更新状态 | 单测：成功/失败/跳过三条路径 |
| 3 | 失败重试与上限；日任务兜底重投 | 停 Qdrant 故障注入；重复任务幂等 |
| 4 | 状态查询/告警 | 失败计数可查；阈值告警 |
| 5 | 现有内容回填（一次性脚本） | 抽样核对 `indexed` 与 Qdrant 点数 |

**风险**：迁移/worker 改动跨 DB 与队列；先做可空列 + 双写，确认稳定后再把 `index_status` 作为判断依据。
**不在本轮做**：跨库原子、自动重建全库向量、视觉塔索引。

---

## 四、与现有工作的关系

- 与 `RAG链路修改建议_20261026` 的 P1/P2「索引可靠性」一致；
- 与 `pipeline._index_after_commit` 的现有「后置、尽力而为」口径一致，不推翻；
- 与 B-2 日常维护 cron 的关系：日任务可增加「重投 failed 索引」，但不在本设计内直接改生产 cron。
