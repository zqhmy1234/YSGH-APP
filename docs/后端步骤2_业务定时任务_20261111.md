## 待确认部署的具体方案

1. 本地通过强制审核后直接提交并推送 `develop`，跟进同一 SHA 的完整 CI 到结束。
   用户看到提交链接、差异、本机验证和 CI 结果后，需单独明确确认本步骤部署。
2. 部署前复查上述文件 SHA256 与 cron hash，若漂移就停止覆盖并比对；保存原文件、
   原 crontab 和本次提交文件清单。仅从确认的 Git 提交导出三个 Python 文件及 cron 范本，
   不同步整仓，不覆盖那 37 个差异文件，不复制本机 `.env` 或备份数据。
3. 用服务器现有 Python/现有环境先执行四项 `--dry-run`，只记录计数。
   确认日志目录已创建且限制权限，再把四条业务 cron 追加至原 crontab，保留备份两条。
   时间分别为每小时 :07、每日 04:10/08:05/22:00，服务器时区 Asia/Shanghai；JSON 时间为 UTC。
4. cleanup 始终 `--dry-run`。即使去掉该参数，入口仍默认预览；正式删除需要另行核准范围
   并显式传 `--execute-cleanup`。保留期内容 30 天、上传残留 7 天。
5. 由新启动的 cron 进程加载 notify 修复；本步骤不重启 API/worker，不触及 Agent，
   不改数据库 schema、依赖或现有备份/WAL 配置。原手动脚本的新进程也使用同一去重逻辑。
6. 部署后用专门验收用户/内容做受控重投、到期胶囊和复盘重复验证，记录计数及结果；
   测试数据清理也限定该用户。至少观察一个完整每日调度周期，逐项核对日志与备份新产物。

回滚：恢复原 crontab（保留原有备份），移除新增维护入口并还原两份已有 Python 文件。
不需要 schema 回滚。已经成功生成的消息保留；回退旧复盘代码会失去重复保护，
因此回滚后保持四业务 cron 未安装，不能继续调用旧复盘定时任务。

仅完成代码、本机测试、推送和 CI 不等于步骤 2 全部验收完成；部署与每日周期观察仍属必需证据。
