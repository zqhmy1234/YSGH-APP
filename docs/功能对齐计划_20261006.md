## 0. 一个必须先立住的事实

**交付文档（MVP 方案 v3 / 深度设计 9 份 / 测试清单 / 用户故事目录）里没有「agent 服务」这个产品角色。**
全文检索 `agent|忆光` 的 66+ 命中全是开发期队友、Agentic RAG（Won't 清单）、开发工具 Key 三种含义。
`agent/` 是 2026-09-23 入库的第三方交付包（出处见 `agent/UPSTREAM.md`）。

因此「对齐」的对象不是「agent 该实现 F1-F9」，而是三件事：

1. **agent 已承担的职责**（对话页 AI Tab，`POST /v1/chat`）——做到设计门禁的水位；
2. **agent 自带的设计外能力**（知识收藏、企微机器人、URL 抓取）——要么接上、要么诚实标注、要么删；
3. **agent 与 backend/client 的边界**——谁做什么，契约是否成立。

## W1 · 记忆域打通（P0 · 📋 待启动 · 本计划最大缺口）

**现状**：agent 的记忆写 `public.memories`，App 全链读写 `public.contents`。
**两张表互不可见**——用户在 AI 页说「记一下我今天去了香山」，这条记忆**进不了**
时间轴、描述性搜索、「去年今日」回响、画像。用户以为记住了，换到 App 里找不到。

这直接违反项目铁律「**假状态比错误更贵**」（`backend/app/services/external/agent.py:9-10`
自己也是这么写的）。Agent 3 逐条核对：agent 侧零画像、零事件聚合、零回响代码。

**方案对比**（需拍板，倾向 B）：

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A. agent 直写 contents | `save_memory` 在写自身表的同时，按 backend 的 contents 形态补写一条 | 即时可见 | agent 需理解 contents 的用户映射/内容形态/去重口径；两套 ID 体系（int vs UUID）要桥接 |
| B. backend 定向摄取（推荐） | agent 只写自己的表；backend 增加一个「agent 记忆摄取」步骤（管线或 RAG 索引前），把 `memories` 中未摄取的行转成 content | 边界干净：数据形态转换归 backend 管；agent 不需要懂 contents | 多一条同步路径，需幂等标记 |
| C. RAG 双源索引 | 检索时同时查两张表 | 不动写入 | 搜索/回响/画像各处都要适配双源，长期最贵 |

**验收**：AI 页保存的记忆，在 App 搜索页与时间轴可见；口径用 02 文档的用户故事表登记移动。
**工作量**：中-大（跨 agent/backend，含 ID 桥接与幂等）。
**依赖**：需确认 AI 页记忆的 `content_type` 归类（建议新增 `chat_memory` 或归 `note`）。

## W2 · Agent 检索升级：复用 backend RAG（P0 · 📋 待启动）

**现状**：`search_memories` 是 **ILIKE 模糊匹配 + 枚举过滤**
（`agent/src/tools/memory_tools.py:595`，`ilike("content", f"*{query}*")`）。
agent 全文 `embedding|Qdrant|BGE|vector|rerank` = **0 命中**。

**差距**：设计 M1 门禁是「检索 Top3 ≥ 70%」（BGE-M3 dense+sparse + 双层 rerank + 溯源，
backend `services/rag/*` 已实现）。**AI 页里用户说「帮我找一下…」走的是 ILIKE**，
能力水位远低于 App 搜索页——同一个"找记忆"，两个入口两副本领。

**方案**：`search_memories` 改为调 backend 检索（HTTP 内呼或直连 Qdrant），
agent 侧只做参数归一（分类/情绪/主题枚举映射）与结果脱敏。
**验收**：AI 页检索复跑 `gate2` 同款口径（Top10 ≥ 88% / hit@1）。
**工作量**：中。**依赖**：backend 检索接口的鉴权方式（服务间 token 已有 `AGENT_SERVICE_TOKEN` 先例）。

## W4 · 部署接线（P0 · 📋 待启动 · 最被忽视的硬缺口）

**现状**：`deploy/systemd/` 只有 `yishu-api` / `yishu-worker`；`deploy/docker-compose.yml`
只有 postgres/redis/qdrant/backend。**agent 服务没有任何部署单元**——
本机能跑（8300），线上不存在。而「客户端 ↔ Agent 接线完成」的验收前提就是它在线上。

连带后果（决策台账 §16.13 自认未验证）：`agent/.env.example:28-29` 记录过
`DASHSCOPE_API_KEY` 错配 ⇒ 后端护栏 401 ⇒ fail-closed ⇒ **每一句 AI 回复都被拦成 422**。
服务不在部署面，这类事故只能靠本机复现才发现。

**要做**：systemd unit（`yishu-agent.service`，含 `EnvironmentFile` 与 `Restart=always`）+
compose 可选项 + 健康检查接 `deploy/scripts/healthcheck.sh` + 启动自检补「backend 可达性」
（现在只报 model/checkpointer/token）。
**工作量**：小-中。**优先级理由**：不接线，W1/W2 的对齐都只能在本机自嗨。

## W6 · Schema 漂移治理（P1 · 📋 待启动 · 有实际破坏性风险）

**现状**：`alembic check` 报 **26 处 `remove_table`** —— `question_history`、
`guardrail_logs`、`audit_log`、`content_tags`、`profile_l2_evidence`、`finetune_jobs`、
`question_templates` 等表**在库里存在但 ORM 无模型**。

**风险**：任何人跑 `alembic revision --autogenerate` 都会生成 **DROP TABLE**——
这不是理论风险，本轮我补索引时就亲眼看到 autogenerate 想删我刚建的索引
（因为 ORM 没声明）。这些表若是真实业务数据，一次手滑就是数据丢失。

**方案**：① 逐表判定「需要 ORM」还是「legacy 待清理」（需与 backend 负责人核对）；
需要的补模型，legacy 的走一次性 DROP 迁移；② 在 backend 测试里加一条守卫：
`alembic check` 的 `remove_table` 清单不得超出已知清单（防新增漂移静默积累）。
**工作量**：中（主要是逐表考古）。**注意**：backend 侧改动应与 backend 负责人协调，
本轮只在 agent 侧建了对拍守卫（`test_agent_schema_alignment.py`，覆盖 agent 三表）。

## 执行顺序建议（按依赖关系，非时间）

```
W4 部署接线 ──┬──> W2 检索升级 ──> W1 记忆域打通
              └──> W3 分类映射拍板 ──┘
W5 企微去留 ──（独立，可与上并行）
W6 schema 治理 ──（独立，建议尽快——它在累积破坏性风险）
```

理由：W1/W2 都要动 backend，且 W2 的接口形态决定 W1 的摄取方式；
W4 是一切线上验证的前提；W5/W6 相互独立、不阻塞主线。
