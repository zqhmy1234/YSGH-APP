3. **agent 与 backend/client 的边界**——谁做什么，契约是否成立。

## W1 · 记忆域打通（P0 · 🔨 写入侧已接入并端到端验证 · 读取侧随 W2 生效）

**现状**：agent 的记忆写 `public.memories`，App 全链读写 `public.contents`。
**两张表互不可见**——用户在 AI 页说「记一下我今天去了香山」，这条记忆**进不了**
时间轴、描述性搜索、「去年今日」回响、画像。用户以为记住了，换到 App 里找不到。

这直接违反项目铁律「**假状态比错误更贵**」（`backend/app/services/external/agent.py:9-10`
自己也是这么写的）。Agent 3 逐条核对：agent 侧零画像、零事件聚合、零回响代码。

**方案对比**（需拍板，倾向 B）：

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A. agent 直写 contents | `save_memory` 在写自身表的同时，按 backend 的 contents 形态补写一条 | 即时可见 | agent 需理解 contents 的用户映射/内容形态/去重口径；两套 ID 体系（int vs UUID）要桥接 |
| B. backend 定向摄取（推荐） | agent 只写自己的表；backend 增加一个「agent 记忆摄取」步骤（管线或 RAG 索引前），把 `memories` 中未摄取的行转成 content | 边界干净：数据形态转换归 backend 管；agent 不需要懂 contents | 多一条同步路径，需幂等标记 |
| C. RAG 双源索引 | 检索时同时查两张表 | 不动写入 | 搜索/回响/画像各处都要适配双源，长期最贵 |

**验收**：AI 页保存的记忆，在 App 搜索页与时间轴可见；口径用 02 文档的用户故事表登记移动。
**工作量**：中-大（跨 agent/backend，含 ID 桥接与幂等）。
**依赖**：需确认 AI 页记忆的 `content_type` 归类（建议新增 `chat_memory` 或归 `note`）。

**本轮已实现（2026-10-06，端到端实测通过）**：采用**方案 A（镜像写入）**——比方案 B
（backend 定向摄取）少一条同步链路，且复用 App 创建函数体使护栏/变更日志/管线
入队**零逻辑复制**；长期是否收敛到单一存储待观察。

- **backend**（`app/api/contents/__init__.py` 末尾）：`POST /api/v1/contents/agent`
  —— **直接调用 `create_content` 路由函数本体**（`agent_service_user` 返回的
  User 类型与 `get_current_user` 一致，函数内只取 `.id`）。这样护栏检测、
  client_generated_id 幂等、变更日志（他端 pull 有源）、RQ 管线入队四件事
  **一字不漏**——任何"照着写一份"的实现都会在某次改动后悄悄漏掉一件。
  `DELETE /api/v1/contents/agent/by-cgid/{cgid}`：按幂等键软删，走同一条
  `sync_writes.soft_delete_content`（四件事一次做齐），**幂等**（未镜像过返回
  `deleted=False` 而非 404，agent 删除不因镜像缺席而失败）。
- **schema**：`source` 枚举扩 `agent`（已核实无消费方按枚举值过滤）。
- **agent**（`memory_tools.py`）：`save_memory` 成功后 `_mirror_memory_to_app()`
  （`client_generated_id=agent-memory-{memory_id}` 确定性幂等键；mood/topics/
  people/category 放 `extra` 随管线进 Qdrant payload；location 进 remark）；
  `delete_memory` 成功后 `_unmirror_memory_from_app()`。两者均 **best-effort**：
  镜像失败只记日志，绝不回滚用户可见的"保存/删除"。
- **端到端实测**（起真 backend + 真实用户）：镜像写入（`source=agent`、
  `content_type=text`、`status=processing` 待管线）、幂等（重复镜像仍 1 行）、
  删除同步（镜像软删 `deleted_at` 置位）——全 PASS。
- **重要发现（安全侧，顺带验证）**：镜像路径**过完整护栏**。本机首次实测被
  422 拒收（托管护栏判定违规），换无害文本后通过——证明 SAF-005 在镜像路径
  **真实生效**：护栏不可用（guard-unavailable）⇒ 拒收 ⇒ App 侧不留未过审内容。
  这也意味着：**镜像依赖可用的百炼 key**，key 失效期间 AI 页记忆只进 agent 表
  （对话内可用，App 侧暂缺），恢复后新记忆自动恢复镜像。
- **agent 侧日志键**：`content_id` 已加入 `observability._SAFE_ID_KEYS` 白名单
  （contents 行的 UUID 标识符，镜像对账必需；实测没加白名单时镜像成功但日志
  被守卫吞掉，对账无从下手）。

## W2 · Agent 检索升级：复用 backend RAG（P0 · 🔨 本轮已接入，待真机观察）

**现状**：`search_memories` 是 **ILIKE 模糊匹配 + 枚举过滤**
（`agent/src/tools/memory_tools.py:595`，`ilike("content", f"*{query}*")`）。
agent 全文 `embedding|Qdrant|BGE|vector|rerank` = **0 命中**。

**差距**：设计 M1 门禁是「检索 Top3 ≥ 70%」（BGE-M3 dense+sparse + 双层 rerank + 溯源，
backend `services/rag/*` 已实现）。**AI 页里用户说「帮我找一下…」走的是 ILIKE**，
能力水位远低于 App 搜索页——同一个"找记忆"，两个入口两副本领。

**方案**：`search_memories` 改为调 backend 检索（HTTP 内呼或直连 Qdrant），
agent 侧只做参数归一（分类/情绪/主题枚举映射）与结果脱敏。
**验收**：AI 页检索复跑 `gate2` 同款口径（Top10 ≥ 88% / hit@1）。
**工作量**：中。**依赖**：backend 检索接口的鉴权方式（服务间 token 已有 `AGENT_SERVICE_TOKEN` 先例）。

**本轮已实现（2026-10-06，端到端实测通过）**：

- **backend**：`app/api/deps.py` 新增 `agent_service_user` 依赖（`X-Agent-Token` 恒定时间比对 +
  `X-On-Behalf-Of` 代执行用户须真实存在且未冻结；token 未配置 ⇒ 503 **fail-closed**，
  绝不裸奔——那条通道能以任意用户身份检索）；`app/api/search.py` 新增
  `POST /api/v1/search/agent`（`include_in_schema=False`，复用**同一个** `rag_search`，
  召回/改写/精排/溯源与用户端点完全一致，不是缩水版）。
- **agent**：`memory_tools._backend_rag_search()` 把 backend 命中（App 侧 contents）
  并入 `search_memories` 结果，标 `source=app_contents` 并给模型 `_hint`（提示措辞
  「你在 App 里记录过」）；backend 不可达/未配置/超时一律**静默降级**为只搜本地表，
  对话不受影响；`AGENT_BACKEND_SEARCH=0` 可整体关闭，超时默认 6s。
- **端到端实测**（起真 backend + 真实用户 151 条 contents）：真命中
  （「在江边散步…」score=0.0164）、错 token 401 fail-closed、无 token 静默降级、
  合并后 `sources={'app_contents': 2}` 且 hint 生效——全 PASS。
- **已知边界**：`SearchHit` 不含情绪/标签（backend `schemas/search.py:19-31`），
  agent 需要时拿 content_id 二次补查；`AGENT_BACKEND_BASE_URL` 默认 8010（生产约定
  `API_PORT=8010`），本地开发（backend 默认 8000）需显式设置。

## W4 · 部署接线（P0 · ✅ 本轮完成）

**现状**：`deploy/systemd/` 只有 `yishu-api` / `yishu-worker`；`deploy/docker-compose.yml`
只有 postgres/redis/qdrant/backend。**agent 服务没有任何部署单元**——
本机能跑（8300），线上不存在。而「客户端 ↔ Agent 接线完成」的验收前提就是它在线上。

连带后果（决策台账 §16.13 自认未验证）：`agent/.env.example:28-29` 记录过
`DASHSCOPE_API_KEY` 错配 ⇒ 后端护栏 401 ⇒ fail-closed ⇒ **每一句 AI 回复都被拦成 422**。
服务不在部署面，这类事故只能靠本机复现才发现。

**本轮已完成（2026-10-06）**：

1. `deploy/systemd/yishu-agent.service`（新文件，按 yishu-api.service 模板约定：
   `@DEPLOY_ROOT@`/`@RUN_USER@` 占位符、`--workers 1` 单进程铁律、
   **绑 127.0.0.1**——agent 自身不鉴权用户身份，暴露公网＝任何人读写他人记忆；
   不设 Memory 限制并注明原因：agent 无本地大模型）。
2. `deploy/scripts/deploy_one.sh`：install_systemd 清单加入 `yishu-agent.service`
   （enable/restart/status 三处同步），并在 agent/.venv 缺失时 warn 提示
   `cd agent && uv sync --frozen`（agent 依赖与 backend venv 互不通用）。
3. `deploy/scripts/healthcheck.sh`：新增第 8 项「Agent /health」探活
   （只探进程存活，不触发建连；降级状态看 /health 的 checkpointer 字段）。
4. agent 启动自检（`main.py` lifespan）：新增 **backend 可达性探测**
   （`GET /healthz`，2s 超时，不阻断只 WARNING）——W1/W2 都依赖 backend，
   它不可达时静默降级的表现是「对话正常但搜不到 App 记忆/记忆不进时间轴」，
   正是最危险的「看起来正常实际是假的」，必须在启动日志里可见。

**上线前置（运维清单）**：① `cd agent && uv sync --frozen`（建 agent/.venv）；
② `deploy/.env` 配 `AGENT_SERVICE_TOKEN`（两个服务同值）与
`AGENT_BACKEND_BASE_URL=http://127.0.0.1:8010`（API_PORT 同值）；③ 有效的
百炼 key（镜像路径过护栏，fail-closed）。

## W6 · Schema 漂移治理（P1 · 🔨 守卫已建，13 张表待逐表判定）

**风险**：任何人跑 `alembic revision --autogenerate` 都会生成 **DROP TABLE**——
这不是理论风险，本轮补 `knowledge_collections.mood` 时就亲眼看到它想删我刚建的索引
（同理，只是对象是表）。这些表若有真实业务数据，一次手滑就是不可逆丢失。

**本轮已做**：新建 backend 守卫 `tests/test_schema_drift_guard.py`（3 用例）——
用 `compare_metadata` 直接取 diff（不解析文本），断言 ①无模型表 ⊆ 已知清单、
②清单不过期、③**agent 三表绝不允许出现在 remove_table 里**。
守卫首跑就抓到一个真问题：我自己的测试漏了 `import app.db.models`（模型未注册
进 Base.metadata），导致 compare_metadata 把 agent 三表判成 remove_table——
这正是 `a4b5c6d7e8f9` 文件头警告的失效形态，也证明这个守卫**能红**。

**剩余**：13 张表逐表判定「补 ORM 模型」还是「确认 legacy 走一次性 DROP 迁移」
（需与 backend 负责人逐表核对，工作量中）。

## 执行顺序建议（按依赖关系，非时间）

```
W4 部署接线 ──┬──> W2 检索升级 ──> W1 记忆域打通
              └──> W3 分类映射拍板 ──┘
W5 企微去留 ──（独立，可与上并行）
W6 schema 治理 ──（独立，建议尽快——它在累积破坏性风险）
```

理由：W1/W2 都要动 backend，且 W2 的接口形态决定 W1 的摄取方式；
W4 是一切线上验证的前提；W5/W6 相互独立、不阻塞主线。
