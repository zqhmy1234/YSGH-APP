# 小模型试点报告（2026-10-25）

> **一句话结论**：`bge-small-zh` 比现用的 `bge-m3` **快 14 倍 / 准 +2 条 / 小 24 倍**；
> int8 量化后 **22.9MB / 4.7ms**，代价是再掉 1 条准确率。

## 背景：为什么要换

用户提出「这部分应该有很快的小模型去做」。实测发现旧认知是个误解：

> 「SetFit 单条推理 27s，只能进 RQ 队列」—— 这是 **`bge-m3` 底座（2.2GB）** 造成的，
> **不是 SetFit 本身**。换底座后单条降到 **10ms 量级**，足以进 API 热路径。

## 实测对比

留出集：**14 条手工构造**（7 类各 2 条，刻意避开训练集典型表述）。
口径：同机房同进程、float16（torch）/ int8（ONNX）、单条串行。

| 方案 | 准确率 | 单条中位延迟 | 体积 |
|---|---|---|---|
| `bge-m3` torch fp16（**现用**） | 9/14 | **138.7ms** | **2182 MB** |
| `bge-small-zh` torch fp16 | **11/14** | 9.8ms | 91.9 MB |
| `bge-small-zh` ONNX fp32 | **11/14** | 10.6ms | 90.4 MB |
| `bge-small-zh` ONNX **int8 per-channel** | 10/14 | **4.7ms** | **22.9 MB** |

**相对现用方案**：torch 版 **准 +2 条 / 快 14× / 小 24×**；int8 版 **准 +1 条 / 快 30× / 小 95×**。

## 量化配置不是随便选的（实测三种）

| 变体 | 准确率 | 体积 | 判定 |
|---|---|---|---|
| int8 **per-tensor**（默认） | 9/14（**-2**） | 22.8MB | ❌ 不可接受 |
| int8 **per-channel** | **10/14（-1）** | 22.9MB | ✅ **最优** |
| uint8 per-channel | 10/14（-1） | 22.9MB | ~ 与上者持平 |
| int8 + 排除 embedding/pooler | 9/14（-2） | 22.8MB | ❌ 更差 |

**为什么 per-channel 必须**：整条模型共用一个 scale 时，embedding 与 attention 里量级差异大的
小矩阵会被同一个 scale 压扁；per-channel 给每个输出通道独立 scale，损伤小得多。
**为什么"排除 embedding"反而更差**：混合精度在短文本上引入额外数值不连续。

## ⚠️ 四条诚实边界（不要把这份报告读成"可以上线了"）

1. **留出集只有 14 条**，手工构造。样本量**不足以做统计显著性** —— 本报告只能做
   **同口径模型间对比**，**不是绝对精度基线**。±1 条都在噪声范围内。
2. **换模型会改变错误分布，不是单纯变好**。现用模型错 `question/fact/mixed` 共 5 条；
   候选错 `idea/fact/mixed` 共 3 条。**上线前必须用真实语料复评**
   （`research/truth-data/b/`，目前 C 批缺标注表见 E-14）。
3. **int8 掉 1 条**是真实代价。若产品不能接受任何精度下降，用 torch fp16（91.9MB / 9.8ms）
   或 ONNX fp32（90.4MB / 10.6ms）—— **依然比现用方案好 14 倍快、24 倍小**。
4. **`classifier.py` 尚未换底座**。本批只做离线对比与产物，运行期仍走 `bge-m3`。
   换底座是单点改动但会影响纠错链路（`class_source` 判据，见 B-07），需一起评估。
