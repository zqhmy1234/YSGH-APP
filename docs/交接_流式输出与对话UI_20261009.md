0. 一句话现状
「App → backend POST /api/v1/chat/messages → agent /v1/chat（DeepSeek/百炼）→ 回复」全链路已在真机跑通（真机 user device:b1fb4b3b32094f7a，多轮上下文、W1 镜像、壳内空态均实测通过）。剩下的两个缺口是流式输出（当前整段返回，用户干等 8~12s）与对话页 UI 结构化（当前回复恒为 kind=plain 纯文本，设计稿的卡片/chips 形态未落地）。

1. 架构与契约现状（改动前必读）
App TabAi（components/TabAi/TabAi.uvue）
  → uni.request POST {BASE_URL}/api/v1/chat/messages   （backend/app/api/chat.py）
      → JWT 鉴权（get_current_user）→ 用户消息落库 chat_messages(role=user)
      → services/external/agent.py::call_agent_chat(user_id, message, conversation_id)
          → HTTP POST {AGENT_SERVICE_BASE_URL}/v1/chat   （agent/src/main.py）
              headers: X-Agent-Token（共享密钥，backend/.env 与 agent/.env 必须一致）
              payload: {user_id, message, thread_id: f"{user_id}:{conversation_id}"}
              ⚠️ thread_id 派生规则是 agent 归属校验（security.py::validate_thread_id）的硬契约，
              只能 = user_id 或以 f"{user_id}:" 开头，乱传即 403「thread_id 不属于当前用户」
      → 生成态输出护栏 screen_generated(deep=true)（services/llm_ops/output_guard.py）
      → 回复落库 chat_messages(role=assistant) → ApiResponse{conversation_id, reply{...}, latency_ms}
回复 kind 枚举（_kind_for，chat.py）：bubble | plain+chips | cards | confirm | typing——客户端 TabAi 按.kind 分支渲染，当前 agent 回复恒为 plain（agent 只回文本）。
流式（SSE）未实现：chat.py 文件头已登记「真流式需 agent 侧 SSE 输出，另批（AG6 余项）」。agent 侧历史上游有 /stream_run（SSE）先例可考（agent/UPSTREAM.md 五）。
客户端请求层：utils/api.uts 全项目 resolve-only（不 reject）+ 10s 看门狗 + 401 single-flight refresh（auth.uts:176-188）。
2. 任务一：流式输出（SSE）
目标
用户发出消息后逐字/分片渲染，替换当前「发出去 → 干等 8~12 秒 → 整段弹出」。

改造点（建议顺序）
agent 侧：/v1/chat 增加 SSE 变体（参考上游 /stream_run 形态，agent/src/main.py 契约注释）。流式内容 = LangGraph agent.astream() / stream() 的 token 增量 + 工具状态事件（tool_started/tool_done，main.py 已有 tool_failed 观测点可复用）。
backend 侧：chat.py 新增 GET /api/v1/chat/replies/{id}/stream 或把 POST 改 SSE 响应（FastAPI StreamingResponse，media_type=text/event-stream）。约束：用户消息落库、护栏 screen_generated、回复落库三件事在流式形态下仍须成立——建议：流式只推"预览"，终稿仍走护栏+落库，客户端以终稿事件收尾。
客户端：TabAi 逐字渲染。⚠️ 蒸汽模式（manifest vapor:true）已知坑：uni.request 桥接可能吞回调/不派发（api.uts:260-261、auth.uts:66-67 两处自证），SSE 若走 uni.request enableChunked 必须先写探针用例验证真机行为；不可用则退路 = 短轮询分片（chat.py 已有 GET /replies/:id 轮询形态，:5-6）。
护栏与流式的相容：screen_generated 是终稿闸门（CHAT_004 拦截），流式预览若提前展示被拦内容 = 设计事故。方案：预览延迟 1~2s 或预览打"生成中"水印，终稿事件到达后整体替换。
验收
真机（adb reverse 联调，见 §4）发消息后 ≤1.5s 出现首字/首片；
多轮上下文不回归（thread_id 派生规则别动）；
护栏拦截路径在流式下仍成立（发敏感内容 → 422 → 无预览泄漏）；
agent 宕机 → 502/504 提示（CHAT_001/002）不伪造回复。
3. 任务二：对话页 UI（结构化回复）
现状与差距
agent 回复是自由文本（含 emoji/工具确认格式），backend _kind_for 判成 plain → TabAi 走纯文本渲染。
设计稿（忆述光华_交付文档 内 AI 对话页帧）的形态：气泡 + chips 快捷操作 + 卡片（记忆卡片）+ typing 态。后端 replies 契约已预留这四种 kind（chat.py:5-7），缺的是「结构化数据的生产」。
改造点
agent 侧结构化：save_memory 成功后让 agent 返回结构化摘要（JSON 或约定分隔格式），backend 据此产出 kind=cards（记忆卡片：内容/分类/情绪/主题）与 chips（追问建议）。⚠️ agent 回复会进 LLM 上下文，结构化标记要用 agent 侧协议而非裸 JSON 拼接（参考 2026-10-08 的 DSML 文本泄漏教训——DeepSeek 曾把工具调用写成文本标记泄进回复；qwen3.8-flash 无此现象但同样要防）。
chips 数据源：从对话上下文生成 2~3 个追问建议（可复用 agent 的 topics）。
typing 态：流式未就绪前的占位（任务一的前置可先落）。
客户端 TabAi 渲染分支补齐 cards/confirm（chips 已有渲染分支，见 _kind_for 与 TabAi 模板）。
验收
记忆类对话回复出记忆卡片（含分类/情绪/主题 chips）；
普通闲聊回复保持 bubble；
空态/异常态不打断会话（conversation_id 保持，切 tab 回来对话不丢——壳内 v-show 保活已由 4bcdcbb 保证，不要在 TabAi 内部再写 redirectTo，B10 铁律「壳内零 redirectTo」）。

5. 必守军规（本项目血泪浓缩，违反即返工）
壳内零 redirectTo（B10 铁律）：任何 tab 组件内不得整页跳转——会销毁壳（对话丢失/闪屏/二段式跳转三宗罪）。跨 tab 用 requestShellTab，浮层用 shellSheetSeq 桥（shell_state.uts，已有先例）。
UTS null 强转军规：getString/getNumber/getJSON 缺字段返回 null，as string/as number 强转即进程死亡——一律 ?? '' 判空（auth.uts:109、240 两代教训）。
resolve-only + 看门狗：UTS Promise 不 reject；网络调用必须带超时（蒸汽模式桥接会吞回调，api.uts:260 自证）。
失败不伪造：agent 不可用 → 502/504 诚实提示；护栏拦截 → 422 不给预览泄漏。
真机证据铁律（台账 4.4）：宣称打通必须有三要素（型号+时间/截图日志/判定），缺前置写"待补"。
console 在 release 包不可见：排障打点要么走 Sentry captureMessage（utils/sentry.uts），要么真机联调用 HBuilderX 运行（dev 构建可见）——别对着 release 包 logcat 找 console（本批浪费过一轮）。
