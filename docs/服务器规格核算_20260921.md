## 0. 结论（可直接采购）

| 项 | 值 | 判据 |
|---|---|---|
| CPU | **8 核**（4 核为底线） | **加核不提升模型吞吐**——`torch.set_num_threads(4)` 与 `OMP_NUM_THREADS=4` 已写死（`backend/app/services/embedding.py:15-16,30`）。8 核的价值只在「API 进程与 RQ worker 并行不互相饿死」+ 缩略图/备份/迁移并行。**不要上 16 核**（纯溢价） |
| 内存 | **16 GB（硬门槛，不可降）** | 常驻模型账 9–11G，见 §2；8G 档会被推理峰值打爆（`embedding.py:6` 自带「16GB 机器实测 OOM」记录） |

| 带宽 | **5 Mbps** | 以 COS 直传为前提（原图不经服务器）；若改本地盘存储需 ≥20 Mbps，见 §5 |
| 地域 | 中国内地节点，包年包月**直接选 1 年** | 规避「≥3 个月」与「剩余有效期」两道备案条件（用户既有判断，本核算不变） |
| 安全组 | 放行 **22 + 8010**；**5432 / 6379 / 6333 严禁公网** | 三个依赖服务容器端口只绑 `127.0.0.1` |

## 1. 核算方法与为什么必须重算

上一轮推荐（8核16G）的依据是「BGE-M3 + SetFit 两个 2.2GB 模型常驻」，**只覆盖了内存账的一部分**。本次按「进程 × 模型 × 峰值」三层重算，多出三类负载：

1. **第三个常驻模型**：SenseVoiceSmall-ONNX（本地声学情绪），前一轮完全没计。
2. **模型按进程数复制**：模型是 `lru_cache` **进程内单例**（`embedding.py:33` `@lru_cache(maxsize=1)`；`classifier.py:35-36` 同款）——**不跨进程共享**。而**搜索是同步的**（`encode_query` 跑在 API 进程，决策 #9 落地注记「搜索保留同步 + 并发上限 4」），所以 **API 进程与 RQ worker 进程各持一份 BGE-M3**。→ 规格核算第一原则：**内测期强制 `uvicorn --workers 1` + 单 RQ worker**，每多一个进程即多一份 ~1.2G。
3. **推理/媒体处理峰值**：torch 激活张量、PIL 缩略图解码、ffmpeg 音频解码、`pg_dump` 备份，均不在常驻账内。

## 2. 内存账（内测 20 人 · 单 uvicorn + 单 worker）

| 负载项 | 归属 | 内存 | 证据 |
|---|---|---|---|
| OS + Docker 引擎 + 日志 | 系统 | ~1.2 G | 估算 |
| PostgreSQL + pgvector｜Redis(AOF)｜Qdrant | 容器 ×3 | 1.0–1.4 G | 文档（交付文档 §3.1：100K 向量 ≈ 128MB） |
| API 进程：**BGE-M3 fp16** + FastAPI | uvicorn ×1 | ~1.5 G | 实测（`embedding.py:35` 注释「fp16，~1.2GB 内存」） |
| worker 进程：**SetFit** + **BGE-M3** + **SenseVoice ONNX** + 框架 | RQ worker ×1 | ~3.3 G | 实测（`classifier.py:39-40`「fp32 实测 2.2GB → fp16 约 1.2GB」；`embedding.py:35`；funasr-onnx 模型 ~0.5–0.9G 估算） |
| 峰值预留：torch 激活 / PIL 缩略图 / imageio-ffmpeg 解码 / pg_dump | — | 1.5–3 G | 实测线索（`embedding.py:6`「CPU 版默认开满核 → 内存峰值超限（16GB 机器实测 OOM）」） |
| **合计** | | **约 9–11 G** | |

**降载预案（若 16G 仍吃紧，按序动手）**：① `uvicorn --workers 1` 已是最低，不得再加；② `ASR_LOCAL_EMOTION_MODE=off` 关本地情绪推理，改由百炼主通道给情绪（省 ~0.5–0.9G）；③ 缩略图并发降 1（省 PIL 峰值）；④ 最后才考虑升配。

## 3. CPU 账（为什么 8 核是「并行」而非「加速」）

| 负载 | 量级 | 证据 |
|---|---|---|
| BGE-M3 查询编码 | 单次几百 ms（全链路搜索 P95 实测 2013ms <3s 门禁） | 文档（08 报告）/ 实测（门禁记录） |
| **SetFit 分类** | **单条 ~27s；批 10 条 ~30s** | **实测**（`classifier.py:106-107` 原注释） |
| SenseVoice ONNX 情绪 | 单段数秒级 | 估算 |
| PIL 缩略图 | 单张 0.5–2s | 估算 |
| webrtcvad 长录音 VAD 分段 / imageio-ffmpeg 解码 | 分段级 | 代码（`requirements.txt`） |

**结论**：SetFit 是最大 CPU 热点 → **分类/裁决必须保持 RQ 异步 + 客户端轮询**（现状已如此，`classify_job` 在 worker）。搜索并发上限 4、DB 池 5+10（`08 报告 §1.1.3` 的 P0-2 修复）为既有护栏，**部署脚本不得擅自放大**。

## 4. 磁盘分账（系统盘 60G）

| 项 | 估算 | 说明 |
|---|---|---|
| 运行环境（pip：torch + transformers + onnxruntime + modelscope + fastapi 栈） | 4–8 G | 估算·上机实测回填（torch 安装后 ~1G，其余为 AI 栈） |
| 模型资产 | 3.8–5.3 G | **BGE-M3 ~2.2G（实测口径：`scripts/warm_hf_models.py:52`「将现场下载 ~2.2GB」）** + SetFit 1.1–2.2G + SenseVoice ONNX 0.5–0.9G（`backend/scripts/prepare_sensevoice.py` 预置）。**reranker（3.2G）不下载**——`RERANK_ENABLED=false` 且 CPU 单对 ~850ms 超门禁（`config.py:148-152`） |
| Docker 镜像（pgvector/pgvector:pg16 + redis + qdrant） | ~1 G | 估算 |
| PG 数据 + WAL + 每日 `pg_dump -Fc` | 3–6 G | 文档（备份策略 RPO ≤24h / WAL ≤5min） |
| OS + 日志 + 余量 | ~10 G | 估算 |
| **合计** | **约 22–31 G** | 余量 ≥25G ✅ |

**COS 模式用户媒体不落系统盘**（原图/音频走对象存储）。若改 `STORAGE_BACKEND=fs`：20 人 × 30 天 × 30–60MB/人/天 ≈ 20–35G 且只增不减 → 需 ≥100G 或挂数据盘（见 §5）。

## 5. 带宽账（5Mbps 成立的前提）

`5 Mbps ≈ 625 KB/s`。

| 流量 | COS 模式（已拍板） | fs 本地盘模式 |
|---|---|---|
| 照片原图上传 | **0**（客户端 STS 直传，不经服务器，决策 #10） | 全过服务器：3MB/张 ≈ 5s，3 人并发即排队 → **需 ≥20Mbps** |
| 缩略图下发 | ~2KB/张，可忽略 | 同左 |
| API JSON | 每次数 KB–数十 KB，可忽略 | 同左 |
| **音频上传（易漏项）** | **部分经服务器**：`client/utils/voice.uts:268-370 uploadVoicePersistent()` 走 `/upload/init→chunk→complete` 分片协议；wav 16k/16bit/单声道 ≈ **1.92MB/分钟**，30min 长录音 ≈ **34MB**（5Mbps 下 ~55s）。**STS 直传（`TENCENT_STS_ROLE_ARN` 已配）为降载项，UPLOAD_005/008 有降级路径** | 同上 + 原图 |

**结论**：5 Mbps 在 COS 模式下成立（低频长录音的中转可接受）；**若 STS 直传未真正生效（UPLOAD_005 降级为后端中转），音频流量成为唯一可观项**——内测 20 人低频，可接受，但须上机实测一次 30min 录音中转耗时并登记。

## 8. 用户手工清单（非 Agent 可代劳）

1. 购买主机（8核16G / 60G / 5Mbps / 中国内地），安全组只放行 22 与 8010。
2. 域名 + 实名认证（主体与备案主体一致）；**并行提交 ICP 备案**（法定 20 工作日，不阻塞内测，今天即可提交）。
3. 生成并保管**自有签名证书**（keystore），记录证书 MD5（备案要用）。
4. 确认 Infisical 生产密钥条目注入方式（JWT / refresh HMAC / 媒体票密钥由 Agent 生成后交用户录入）。
5. 20 位内测用户名单 + 反馈渠道（企微群或邮箱）。
6. 关闭机器上的「纯净模式」相关提示或准备内测说明（EMUI 拦 `adb install` 且零报错——用户侧安装需先关）。
