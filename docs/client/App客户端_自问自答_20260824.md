## Q1：客户端现在到底写到什么程度？一行代码没写？

**答：基本是"零特性代码"，但"架构原型已验证"。**

- `session-handoff.md` 明确："**客户端（APP/Windows）整体未启动；后端 API 约 70% 就绪**"。
- `feature_list.json` 中三个**必须靠客户端代码**的特性全部 `not-started`：
  - **F1** 照片自动读取分类（P0，需相册监听+端侧聚合）
  - **F8** 时间轴展示（P0，需 UI 渲染 L1/L2/L3）
  - **F9** Windows 桌面端（P1，需 Electron+Python sidecar）
- 其余 in-progress 的 F2/F3/F4/F5/F6/F7/P2-ECHO 都是**纯后端**能力（分类/ASR/RAG/微信找/冷启动/回响/同步），不依赖客户端。

> 所以严格说：客户端不是"一行没写"，而是**还没有进入任何 feature 的开发态**——已有的只是 POC 阶段的一次性探索工程（`research/poc/android/`，24MB 最小 APK），不是产品代码。

## Q2：后端热火朝天（210 测试全过），客户端一动不动——是不是架构没定？

**答：架构早就定了，而且是被 POC 锁死的，不是没定。**

- 技术栈在 `AGENTS.md` 已拍板、明文写死："**前端 uni-app x 双轨（Vue UI 层 + 自研 UTS 插件系统能力层）→ Android 主端**"。
- 决策依据 = 开发决策清单 #2（uni-app x 双轨 + POC 前置关卡），D7 POC 已 GO（见 Q3）。
- 真正的原因是**优先级排序 + 人力分配**，不是技术不确定性：
  - 后端先把"无客户端也能验证"的硬骨头啃了（分类/检索/语音/同步/护栏），这些是 M1/M2 门禁主体；
  - 客户端特性（F1/F8/F9）天然排在"后端管线就绪"之后才有意义——照片要先能分类、事件要先能聚合，时间轴才有的看。

## Q3：那个"全局 Gate / UTS POC"是什么？过了没？过了怎么还不写客户端？

**答：过了，2026-08-17 判 GO，五测全 PASS。Gate 已清，剩下的不是"能不能"，是"谁去写"。**

Gate 内容（`D7_POC结论.md`）：验证 uni-app x 双轨里"系统能力层"（自研 UTS 插件 = 原生 Kotlin）三条硬路径在 Android 真机跑通。

| # | 测试项 | 结果 | 真机 |
|---|---|---|---|
| POC-01 | 相册监听（ContentObserver） | ✅ PASS | nova 11，≤9s 触发 |
| POC-02 | 前台录音（前台服务） | ✅ PASS | nova 11，灭屏 13s 完整 |
| POC-03 | 媒体归因 tag（Android 16） | ✅ PASS | 模拟器 API36 + nova11 |
| POC-04 | SQLCipher 加密 | ✅ PASS | 密文无泄漏 / 错钥拒绝 |
| POC-05 | 事件聚合 spike（ST-DBSCAN） | ✅ PASS | 150→500 张 3ms |

判定规则：POC-01/02/03 任一不过 → 切原生 Kotlin/Flutter；全过 → GO。现五测全过，唯一出口即 GO。

**为什么 Gate 清了还不写：** D7 结论里写得很直白——"UTS 插件人力（原生 Kotlin）"是铺开后的长期瓶颈，但"用户 = T2（具备能力）；T3 交叉学习已列入 Sprint 1 计划"。即能力在、人也在，只是**还没把人力从后端切到客户端排期**。这是项目调度问题，不是技术阻塞。

## Q4：四层事件聚合，端侧/云侧怎么切？ST-DBSCAN 在手机上跑会不会卡/耗电？

**答：L0/L1 端侧、L2/L3 云侧；ST-DBSCAN 不是性能问题（实测 3ms/500 张）。**

切分（`MVP方案_v3.md` F1 行 + AGENTS.md 技术栈注释）：
- **端侧 L0 瞬间**：ST-DBSCAN（参数 60min / 500m / min_pts 3）在手机本地聚"同一时空瞬间"；
- **端侧 L1 日卡片**：当日聚合；
- **云侧 L2**：LLM 语义归并；**云侧 L3**：主题流。
- photo↔event 多对多（`feature_list` F1 描述）。

性能实锤：`D7_POC结论.md` POC-05 "150 张→500 张 **3ms**，预算 2s"；后续升级为 M1 Part 1 正式原型（497 张真实截图基准 15 项验证全过）。**3ms 量级，耗电可忽略**——真正要管的是"端侧聚合的触发时机"（新照片到达时增量跑，不是全量扫）。

> 注意：L2/L3 当前在后端只落了**候选级 draft**（`progress.md` P2-07：`generated_by=cloud-proto`，LLM 语义归并待真实数据到位）。端侧 L0/L1 算法本身已验证，但"端侧跑 + 上传 + 云侧归并"的**闭环尚未联调**（因为客户端没启动）。

## Q5：如果今天要启动 App 客户端，第一步干什么？从哪个 feature 切？

**答：从 F1 切，但第一步是"把 POC 探索工程升级为产品骨架"，不是直接写业务。**

依据 `AGENTS.md` Startup Workflow + `feature_list` DoD 纪律（一次只做一个特性、必须有验证）：

1. **先起四端工程骨架**：M0 已规划"四端工程骨架"，但 feature_list 里 M0 的 evidence 只提到"OpenAPI 契约 14 路径 + mock"，**没提 Android 工程骨架落地**——这是 M0 实际遗留项（POC 工程 ≠ 产品骨架）。
2. **F1 作为第一个客户端 feature**：相册监听（ContentObserver，POC-01 已验证）→ 端侧 ST-DBSCAN（POC-05 已验证）→ 调用后端 `POST /api/...`（契约已发布）→ 时间轴先不急着做，先把"照片进得来、事件聚得出来"跑通。
3. **验证先行**：`init.sh` 只验后端；客户端需要自己的启动校验（能否连后端 mock、能否触发导入）。

> 关键卡点：F1 的 M1 门禁是"**30s 首批事件（≥50 张）+ L1/L2 正确率**"——这条现在因客户端未启动**无法达成**，是 M1 时间线的最大暴露面（见 Q7）。

## Q6：Windows 桌面端（F9）和 Android 主端什么关系？两套代码？

**答：两条独立交付线，不是一套。Android 主端是产品核心，Windows 是 P1 导入补充。**

- **Android 主端**：uni-app x 双轨（Vue + UTS/Kotlin），用户日常使用的主入口。
- **Windows 桌面端（F9）**：`Electron + Python sidecar`（JSON-RPC 2.0 v1）+ PP-OCRv5 mobile 20MB，**定位是"批量导入/桌面照片搬运"**，不是日常主端（`MVP方案_v3.md` F9 行 + B5-e）。
- 两者共享**后端 API + B4 同步协议**：Windows 导入的内容走同一套 COS 分片/对账/软删逻辑（`progress.md` B4 已后端就绪）。
- 隐私差异（`MVP方案_v3.md` Q10）：Windows 端 OCR/本地处理可**完全规避**上云；Android 端 OCR 走云厂商需隐私文案。

> 建议切分：Android 主端进 M1 主线；Windows 进 M4 联调（F9 门禁"OCR 置信度门控 + 断电续传"与 M4 同步一致性强相关）。

## Q7：客户端没启动，对 M0–M5 时间线有什么影响？MVP 扛得住吗？

**答：M0 实质未闭环、M1 暴露面最大；但只要 W3 起排客户端，时间线仍可救。**

| 里程碑 | 周 | 客户端相关门禁 | 当前风险 |
|---|---|---|---|
| M0 | W1-2 | POC GO ✅ / **合规三申请提交 ❌** | POC 过，但"合规申请提交"Gate 未满足（`feature_list` M0 evidence："合规三申请待提交"；`session-handoff`："未启动，5-6 周串行"） |
| M1 | W3-6 | F1：30s 首批事件 ≥50 张 | **F1 not-started，门禁无法验证** |
| M2 | W7-12 | 管线打通 + 分类精度 | 后端管线已通，client 无影响 |
| M3 | W13-15 | 微信收+找 10s/3s | 找=后端 RAG 已就绪；收=企微回调（需 appid/secret，与客户端弱相关） |
| M4 | W16-17 | 端间同步一致 + 断电续传 | B4 后端就绪，但**无客户端无法端到端验证** |
| M5 | W18 | 数据安全全绿 + P0 全过 | 安全含客户端（密钥/存储），客户端缺则 M5 门禁缺一块 |

**结论**：技术风险已清零（POC GO + 后端 70%），**唯一真实风险是"排期 + 合规"**。M0 的合规申请是 5-6 周串行硬依赖，现在还没启动——这才是比"客户端没写"更该盯的炸弹。

## Q8：测试清单里客户端要过哪些 P0？后端现在能替客户端验证多少？

**答：客户端 P0 集中在 F1/F8/F9；后端已替"算法/契约"验了一大半，但"端到端行为"验不了。**

测试清单（`AGENTS.md`）：17 模块 ~140 项，P0 ~60。客户端强相关 P0：

- **F1**：30s 首批事件（≥50 张）+ L1/L2 正确率 → 后端已验"聚合算法"（POC-05 / M1 Part1），**但未验"真机相册→上传→聚合"链路**。
- **F8**：时间轴流畅 + 事件结构正确 → 后端 `events` API 已返真实数据（`progress.md`），**UI 渲染未做**。
- **F9**：OCR 置信度门控 + 断电续传 → 后端 COS 分片/对账已验（`OPS-SECRETS` evidence S5-03/04），**端侧 Electron 未做**。

后端能替客户端"证明算法和契约正确"，但**证明不了"用户在真机上点得动、跑得顺"**——这是客户端必须自己补的验证，无法用后端测试替代。

## Q10：现在最该堵的缺口/风险是什么？（一句话版）

按"影响 × 紧迫"排序：

1. **合规三申请（企微认证/ICP/软著）**：M0 硬依赖、5-6 周串行、至今未启动 → **最该立刻推**，否则 M5 前全链路卡死。
2. **客户端排期切换**：F1 not-started 直接顶着 M1 门禁 → W3 起必须把 T2/T3 人力从后端切到 Android 骨架+F1。
3. **真机数据缺口**：50 条查询 / 100-200 碎片 / 20-50 录音 / 照片+事件真值（`session-handoff` 待团队项）→ 后端已就绪但无数据校准，门禁硬依赖。
4. **文档 drift**（Q9）→ 低危但便宜，顺手修。

## 总判定

> **客户端不是"技术不确定"，而是"排期未启动 + 合规未动"。** 架构层（uni-app x 双轨 / UTS POC / 四层聚合 / 端云同步）全部已被 POC 与后端原型验证通过；现在缺的是**把人力从后端切到客户端 + 启动那条 5-6 周的合规串行线**。这两件事定了，MVP 时间线就还能救；不定，M0 Gate 和 M1 门禁会先爆。
