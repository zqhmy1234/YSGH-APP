## 二、B1 的复现与判据（最容易误判的一条）

```powershell
Test-NetConnection 127.0.0.1 -Port 6379 -InformationLevel Quiet   # True（假活）
python -c "import redis; r=redis.Redis(host='127.0.0.1', port=6379, socket_timeout=3); print(r.ping())"
# TimeoutError: Timeout reading from socket
Get-NetTCPConnection -LocalPort 6379 -State Listen | Select OwningProcess
# → com.docker.backend（Docker 的端口代理；容器里的 Redis 已经不应答）
```

**不要**把"端口通"当成"Redis 可用"；也不要因为 `--full` 挂住就判"测试坏了"——先按 B1 验一次。

## 三、B3 的现场（为什么这轮 BGE 只能单进程）

- `FreePhysicalMemory` = **0.4GB / 15.7GB**。
- 两个 BGE 进程（各 ~1.2GB）并行 = 必然换页/被 OOM kill（项目历史：满核线程曾在 16GB 机器 OOM）。
- 因此回填/压测**一次只跑一个** BGE 进程；要并行必须先释放内存（关 Docker/编辑器）再复测。

| 分类 | 条数 | 说明 |
|---|---|---|
| 无 `cos_key` | **827** | 合成/种子行，永远无法 caption（重投只会失败） |
| 有 key、盘上无文件 | **753** | 对象已丢（存储迁移/清理），重投也失败 |
| 有 key、文件存在 | **114** | **唯一可回填集合** |
| 合计 | 1694 | 与台账旧数 1691 差 3（新数据） |

`--only-empty-done` 只解决"别和 failed/processing 混跑"；`--require-file` 才解决"别对没文件的行空转"。

## 五、处置顺序（建议）

1. **先解 B1**：让 Redis 真正可用（恢复 Docker 或改指 6380），否则 worker/全量门禁都是假的。
2. **再解 B3**：跑重活前释放内存；固定"单 BGE 进程"纪律。
3. **用 114 跑回填**（已在跑），不要用 1694。
4. **B2** 单独起 agent 服务再谈 AI 链路验收。
5. **B5/B6** 是数据治理，与 B-2 的 cron 上线绑定，先 dry-run 分批。
6. 以上解决后，再跑一次 `--full` 钉基线（B7）。
