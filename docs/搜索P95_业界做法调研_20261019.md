# 搜索 P95 调研：GitHub 优质项目怎么做（2026-10-19）

> 目的：为「P95 5560ms → <3000ms」找可落地的业界做法，而不是继续在本地调参。
> 我们的分阶段实测（`docs/性能验收_搜索_20261016.md` 治理后基线）：

| 阶段 | P95 | 说明 |
|---|---|---|
| rewrite | 1361ms | LLM 改写 + 路由/类目判定 |
| encode | 1140ms | BGE-M3 dense + sparse（CPU，4 线程） |
| recall | 886ms | 向量召回 + PG 兜底 + 溯源组装 |
| rerank | 1870ms | bge 粗排 + qwen-flash LLM 精排 + 规则敏感过滤 |
| answer | ~1000ms | 1.0s 硬上限（仅 want_answer） |
| **端到端** | **5560ms** | 单用户顺序压测 |

结论先说：**瓶颈不在 Qdrant，而在「串行 LLM 往返」和「CPU 双前向编码」**。业界项目的共同做法不是"把一步做快"，而是**砍掉不必要的串行步骤 + 把融合下推到向量库 + 换更小/更快的推理栈**。

---

## 一、Qdrant 官方：混合检索一次往返（prefetch + RRF）

Qdrant 1.10 起的 **Query API** 支持 `prefetch` + `query: {rrf: {}}`：dense 和 sparse 两路召回在**服务端**做 RRF 融合，客户端只发一次请求。
官方文档给的形态就是 `prefetch=[sparse, dense]` → `rrf` → `limit`，并说明 prefetch 可以嵌套。
来源：[Hybrid Queries — Qdrant](https://qdrant.tech/documentation/search/hybrid-queries/)

**对我们**：现在是 dense、sparse 两次请求 + 客户端 RRF（`rag/__init__.py`）。改服务端融合能省一次网络往返与一次结果合并，recall 段预计 886ms → ~500-600ms；代码也更短。
**注意**：我们用的是 named vectors（`text_vec`/`image_vec`/`text_sparse`），Query API 支持 `using` 指定，迁移成本低。

## 二、FastEmbed：ONNX + 量化 + 并行，是 CPU 编码的标准解法

Qdrant 的 FastEmbed 用 ONNX Runtime 跑嵌入模型（而非 PyTorch），支持量化模型、`parallel` 多 worker、`batch_size`、`lazy_load`；GPU 版还支持多卡分片。
来源：[Optimize FastEmbed Throughput](https://qdrant.tech/documentation/fastembed/fastembed-optimize/)、[FastEmbed Rerankers](https://qdrant.tech/documentation/fastembed/fastembed-rerankers/)

**对我们**：BGE-M3 的 CPU 前向（encode 1140ms，且查询侧 dense/sparse **各跑一次**）是第二大瓶颈。
两条路：
1. **ONNX/int8**（fastembed 同款思路）：单次前向通常有 2-4× 提升，encode 有望 1140 → 300-500ms；
2. **合并查询侧双前向**（我们已立项未做）：dense 和 sparse 共用一次 encoder forward，省一次前向。

⚠️ 质量风险：int8 需要重跑 R-9 / 50 条真值，确认 `hit_rate@3` 不塌。

## 三、Onyx（原 Danswer）：混合检索是"索引后端的能力"，不是应用层拼装

Onyx 把 hybrid retrieval 实现在 document index 抽象里（Vespa / OpenSearch 双实现），应用层只调 `hybrid_retrieval`；Vespa 负责关键词+向量的融合与排序。
来源：[Onyx PR #6750 — Implement hybrid_retrieval for Vespa](https://github.com/onyx-dot-app/onyx/pull/6750)、[Onyx document search backends](https://deepwiki.com/onyx-dot-app/onyx/8.5-document-search-and-indexing-backends)

**对我们**：与 Qdrant Query API 同一条原则——**把融合放在检索后端**，应用层不重复实现 RRF。我们目前是应用层 RRF + 两次调用，属于"应用层拼装"，既慢又难调权重。

## 四、RAGFlow：混合检索 + 精排是标配，但社区实测它就是慢

RAGFlow 的检索链路是「多路召回（向量/全文）→ 融合 → rerank 模型」；其 issue 里有多起"retrieval process very time-consuming"的反馈，典型原因就是 rerank 与多路召回的串行开销。
来源：[RAGFlow Retrieval and Search System](https://deepwiki.com/infiniflow/ragflow/9-retrieval-and-search-system)、[Issue #10892](https://github.com/infiniflow/ragflow/issues/10892)、[Reranking and Filtering](https://deepwiki.com/infiniflow/ragflow/9.3-reranking-and-metadata-filtering)

**对我们**：我们的 rerank 段 1870ms 里，qwen-flash LLM 精排是"再来一次 LLM 往返"——比 RAGFlow 的本地 cross-encoder 更贵。业界共识是：**精排要可关、可降级、按候选量触发**，而不是每条查询都跑。

## 五、语义缓存（GPTCache 一类）

对"同一用户短时间内重复/近似查询"做向量级缓存，命中直接返回，不进入管线。
来源：[zilliztech/GPTCache](https://github.com/zilliztech/GPTCache)

**对我们**：MVP 内测用户量小，命中率有限；但"搜索历史 + 继续上次搜索"已经在产品里，**同查询缓存**（精确 key）成本极低，可作为兜底。

## 六、把做法映射到我们的四条路（按收益/风险排序）

| 优先级 | 改动 | 预计省 | 风险 | 验收 |
|---|---|---|---|---|
| **P0** | **投机式并行召回**：原查询先召回，LLM 改写返回后若不同再补一轮（或规则命中时跳过改写） | 1.1–1.4s（rewrite 段） | 改写质量下降 → 召回变差 | R-9 50 条 + hit_rate@3 不回退 |
| **P0** | **精排策略化**：LLM 精排只在「候选 >K 或召回置信低」时触发；默认走本地 bge 粗排或直接关 | 1.0–1.9s | 复杂查询排序变差 | 50 条真值对比 + 人工抽 20 |
| **P1** | **BGE-M3 ONNX/int8**（fastembed 路线） | 0.6–0.8s（encode） | 质量损失 | R-9 + 50 条真值 |
| **P1** | **Qdrant Query API 服务端 RRF** | 0.2–0.4s（recall） | 迁移/兼容 | 同一批查询结果 diff |
| **P2** | 查询改写缓存 + 精确查询缓存 | 命中即 ~0 | 缓存污染 | 命中率/回退策略 |
| **P2** | GPU 部署（encode/rerank 数量级下降） | 大 | 成本 | 部署机 P95 探针 |

**组合预期**：5560 − 1300（rewrite）− 1000（精排）− 600（encode）− 300（recall）≈ **2.3–2.6s**，落在 3s 内；但这只是估算，**必须以同一实例、同一语料、n≥20 复测**。

## 七、不建议做的

- **异步二次排序（首响先回 recall，重排后推送）**：要改客户端协议，在野 APK 无此能力；已拍板不做。
- **把 rerank 换成更大的模型**：CPU 上只会更慢。
- **只调 `torch.set_num_threads`**：满核曾 16GB OOM，且收益不稳定。
- **在应用层继续调 RRF 权重**：融合下推后这套代码会消失，调参是白工。
