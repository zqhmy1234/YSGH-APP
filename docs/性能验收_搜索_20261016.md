- want_answer=off：**P95=5560.6ms ≥ 3000ms，不达标**（RET-018）。

- 瓶颈（off 模式口径）：检索段 P95=3863ms ≥ 之后阶段 P95=1987.0ms ⇒ 瓶颈在**改写+编码+召回+组装**（BGE-M3 本地推理与 Qdrant 往返主导；细分到改写/召回需后端补打点）。

## 建议

1. 后端在响应中暴露分阶段打点（改写/召回/rerank/回答各自耗时）——当前只能拿端到端与检索段两点做差，瓶颈定位精度受限（本报告已按'未暴露'如实标注，未编造）。
2. 若检索段成为瓶颈：优先排查 BGE-M3 本地推理耗时（CPU/GPU 档位）与 Qdrant 单次往返；若精排段成为瓶颈：LLM 精排可改异步或换更快的模型档。
3. 本压测为单用户顺序负载（无并发排队）；生产多并发下信号量排队会抬高尾延迟，建议补一轮并发阶梯压测（1/5/10 并发）。

### BGE 档位核查结论（`backend/app/services/embedding.py` 只读核查，未改行为）

- **device**：`SentenceTransformer(MODEL_NAME, model_kwargs={'torch_dtype': fp16})` 未传 `device=` ⇒
  由 sentence-transformers 自动选（有 CUDA 用 GPU、否则 CPU）；当前本机**走 CPU**。
- **CPU 线程**：硬编码 4 线程（`torch.set_num_threads(4)` + `OMP/TORCH_NUM_THREADS` setdefault=4），
  注释记载满核曾致 16GB 机器 OOM ⇒ 调大是**资源决策**须配合内存复测。
- **batch**：`encode_dense` 未传 `batch_size` ⇒ ST 默认 32；检索查询侧单条编码，batch 无收益。
- **查询侧双前向**：dense（encode）与 sparse（tokenize+model[0]+linear）各跑一次前向，可合一（改实现，另立项）。
- 建议（待拍板，不动代码）：① `settings` 化 `BGE_DEVICE/BGE_THREADS/BGE_BATCH_SIZE` 三档；
  ② worker 启动时预热加载模型（检索首请求不再吃懒加载冷启动）；③ 若部署机有 GPU，迁 GPU+fp16 档位预期 encode 段数量级下降。

### 精排异步方案（立项③ · 仅方案不改码）

1. `rerank` 段（off 模式第二大头，含 LLM 精排往返）改**异步二次排序**：首响返回 recall 段结果（P95 可降 ~2s），LLM 重排后经 SSE/轮询推送新顺序——代价是动客户端协议，在野 APK 无此能力。
2. MVP 内更稳的替代：**LLM 精排加 settings 显式开关**（现仅 `rerank_auto_enabled` 隐式自门控），P95 紧约束场景（真机弱网）可服务端整体关断精排换确定性 <3s。
3. 若保留精排：qwen-flash 精排并发化/超时收紧（当前单次往返波动即秒级），与 `answer` 段共用 1.0s 硬上限口径。

## 治理②：决策与实现（2026-10-19）

### 已拍板（本轮，不再等）

| # | 议题 | 结论 | 理由 |
|---|---|---|---|
| 1 | BGE 档位 | **默认保持 CPU + 4 线程**；`device` 改为 settings（空=自动，有 CUDA 自动走 GPU） | 满核曾在 16GB 机器 OOM（`embedding.py` 头注）；GPU 是部署侧资源决策，代码只留开关 |
| 2 | 预热 | **新增 `BGE_WARMUP_ON_START`**（默认关，部署/压测机建议开），启动后台线程预热 | 首请求冷启动实测 12~14s；预热异步化后不阻塞 API 就绪 |
| 3 | 精排异步 | **不采用**"首响先回 recall、LLM 重排后推送"方案 | 要改客户端协议，**在野 APK 无此能力**；MVP 用既有显式开关降级：`RERANK_ENABLED=false`（默认）+ `RERANK_LLM_ENABLED` 可整体关断 LLM 精排 |
| 4 | 查询侧双前向合并 | **本轮不做**，单独立项 | 牵动 dense/sparse 一致性与稀疏权重实现，收益约 0.5s，风险不对等 |

### 已实现（代码 + 验证）

- `app/core/config.py`：新增 `BGE_DEVICE` / `BGE_THREADS` / `BGE_WARMUP_ON_START`（默认 `""`/`4`/`false`，**默认行为与改前逐字一致**）。
- `app/services/embedding.py`：线程数改读 settings（仍默认 4）；`device` 仅在显式配置时传入；新增 `warmup()`。
- `app/main.py`：`lifespan` 内按开关起 daemon 线程预热，失败只 WARN（检索退回懒加载）。
- 实测（2026-10-19，本机 CPU）：`embedding.warmup()` = **9.9s**（加载 + 一次编码），与首请求冷启动 12~14s 同量级 ⇒ 预热能把这 10s 从"用户首搜"挪到"启动后台"。

### 仍未解决（如实）

- **P95 目标仍未达标**：最新真 key 实测 off P95 **5560ms**（上文），warmup 只消首请求冷启动，**不改变稳态 P95**。
- 稳态瓶颈排序（P95）：`rerank` 1870ms > `rewrite` 1361ms > `encode` 1140ms > `recall` 886ms。
- 要真正进 3s，只剩三条路：① 部署机上 GPU（encode 数量级下降）；② 关 LLM 精排（`RERANK_LLM_ENABLED=false`，牺牲换序质量）；③ 改写段降模型/规则化。**这三条都是产品/成本决策，本轮不擅自改默认值。**

### 测量方法

- 数据：

| ① 改写开 + 精排开（原默认） | 0.837 | 0.954 | 0.888 | 4136ms | **5150ms** |

### 判读

1. **关掉 LLM 改写是净赚**，不是权衡取舍：又快又准。原因推测（未单独验证）：改写会把
   时间/地点限定词扩写或替换（如「上上周在北海道滑雪的照片」→ 泛化成「滑雪 照片」），
   导致 dense 向量漂移；而 sparse 塔本来就能靠原词命中，双路召回里原查询一路被改写版的
   高分压过。
2. **精排必须保留**：③ 比 ④ 少 2 条 hit@3（0.930 vs 0.954）。精排贡献约 **2693ms**，
   但换 2 条命中，在当前质量水平下值得。
3. **④ 仍未进 3s**（3335ms）。剩余瓶颈是 ncode（BGE-M3 本地推理）+ Qdrant 往返 +
   精排。要真正进 3s 只剩：部署机 GPU、或按查询长度动态跳精排（需分层实测，本批未做）。
