## 0. 先讲清原因：recall@3=0.0626 为什么这么低

### 0.1 指标口径错配（占大头，结构性上限）
当前 recall 定义（metrics.py）：`recall@k = |相关 ∩ Top-k| / |相关总数|`，而 run_eval.py 的"相关集" = 显式 expected id ∪ **expected_label 对应的全部语料**（15~20 条/类）。

- Top-3 最多命中 3 条 → recall@3 **理论上限 = 3/15~3/20 ≈ 0.15~0.20**。实测 0.0626 = 上限的 ~40%。
- 同一批查询：hit_rate@3=0.7273（73% 的查询 Top-3 至少 1 条相关）、mrr=0.6621、precision@3=0.3939——**排序本身不差**。
- 结论：产品语义是"找一条/几条相关记录"，不是"把某类记录全召回"。recall 分母用类全集，是任务口径（类检索 vs 单条检索）错配。**先修尺子，再谈提升**。

### 0.2 三个真实病灶（决定 recall 天花板的实际短板）
| 层 | 现状 | 根因 | 性质 |
|---|---|---|---|
| descriptive | hit_rate@3=0.5（4 挂 2） | 释义查询与语料零词元重叠：sparse 零命中、dense 距离超阈 → **相关文档根本没进候选集**，任何重排都救不回 | 召回层失效（query 侧） |
| typo | hit_rate@3=0.5（2 挂 1） | 单字错（奶→乃）dense 可容错；多字错（收房祖→收房租）dense 不可靠、sparse 零容忍 | 召回层容错不足 |
| keyword | hit_rate@3=1.0 但 precision@3=0.44 | 字面命中已有，但 dense 语义近邻把噪音排进 Top-3 | 排序噪音 |

> 已修完不再占坑：length 层（0.5→1.0）、时间正则误伤、rerank 静默失效、关键词精确命中提升。

## 1. 对症下药（按性价比排序）

### P0-A 启用并验证 LLM 查询改写（杠杆最大，零开发）
- **原因**：descriptive 层失效点在"召回前"——"关于做产品的想法"和 idea 语料没有共同词，改什么都没用，得把查询改写成与目标分布同词表的表达。
- **现状**：`rewrite_query` 已接 dashscope 且 **key 已配、MOCK=false（活的）**；`_rewrite_query` 已调用，但属"静默可选"路径，从未验证过输出质量。
- **动作**：
  1. 探针：打印 4 条 descriptive 查询的 LLM 改写结果，核对词元重叠率与 dense 相似度提升。
  2. 门禁：改写后查询与目标 label 语料的词元重叠 > 0（现在是 0）。
  3. 延迟：qwen-flash 单次改写 ~几百 ms，P95<3s 预算内，需实测记录。
- **预期**：descriptive hit_rate@3 0.5 → 0.75~1.0；整体 hit_rate@3 0.73 → 0.82~0.91；mrr 0.66 → 0.75+。

### P0-B 修正 recall 口径（先修尺子）
- **动作**：`_resolve_relevant` 双模式——
  1. 有显式 expected id → 相关集 = expected id（单条检索口径，recall 分母变成 1~3 条）。
  2. 仅 expected_label → 保留 label 全集，但单独计为 `recall_diagnostic`，不进门禁。
- 产品门禁口径 = hit_rate@k + mrr + precision@k；recall 改为诊断指标（防"召回某类全部"的伪需求干扰调优）。
- **预期**：显式口径 recall@3 预计 0.5~0.7，且不再随语料扩容虚降。

### P0-C typo 层：查询侧纠错改写
- **动作**：rewrite_query 的 system prompt 增加纠错职责（qwen-flash 对拼音/近音错字纠正强），先零开发试；无效再上 pypinyin 查询侧拼音扩展（候选音向量与查询向量比对）。
- **预期**：typo hit_rate@3 0.5 → 1.0。

### P0-D keyword 层 precision：命中加权梯度化
- **动作**：
  1. `_boost_exact_matches` 增加部分命中梯度（2/3 词元命中 → ×1.3，全命中维持 ×1.8）。
  2. rerank 保持默认关（CPU 40s/查询不可行）；记录 rerank_max_candidates=5 时的延迟-质量权衡数据备用（~4s，仍超门禁，仅作 GPU 前的最优解参考）。
- **预期**：keyword precision@3 0.44 → 0.6+。

### P1-A SetFit 类目路由（召回侧结构性修复，CPU 可行）
- **原因**：descriptive 查询本质是"找某类内容"，而类信息 pipeline 已算好（content_class），检索时没用——33 条 voice 干扰项与目标类文档竞争 Top-3。
- **动作**：描述性查询 → SetFit 分类 → label 过滤/加权 → 干扰项挡在召回路外。**置信度低时回退全量**（防误过滤，沿用 NER 空结果回退的既有模式）。
- **预期**：descriptive 层相关集缩小到类内（~16 条），Top-3 上限从 3/33 提到 3/16；recall 与 precision 双升。

### P1-B 真实评测集替换（尺子校准，等产品部数据）
- 产品部 50 条真实查询 + 100~200 条真实碎片（规格已定：docs/真值数据规格标准_v1.md A 批）。
- **补洞**：benchmark payload 现在无 taken_at → temporal 层测试是"空结果即正确"的空壳，真实数据必须带时间字段。
- 50 条查询下指标波动从 ±0.09 降到 ~±0.02。

### P1-B2 外部基准补充（2026-08-25 核实：hf-mirror 可达，候选已验）

**定位**：主评测永远是产品部真实数据；外部基准只做"补充基线 + 回归哨兵"，不进 M1 门禁，不替代真实集。选择标准：中文、检索任务（非生成）、短段落、带 qrels、可经 hf-mirror/ModelScope 下载。

### 2026-08-25 · BUG：LLM 链路静默失效（403）→ 修复

**现象**：eval 后探针 rewrite_query 全返回 403 Workspace access denied。
**根因**：①机器 User 环境变量残留旧格式 DASHSCOPE_API_KEY（sk-4980...）覆盖 backend/.env 的 sk-ws-（pydantic env 优先）；②dashscope SDK 只认 env/全局 api_key，代码从未同步 settings——双重坑，且 except RuntimeError 静默吞掉，eval 成绩误归因。
**修复**：①删除 User 级旧变量（skill 已记录该残留为已知隐患）；②dashscope.py 新增 _ensure_api_key() 在 _chat_text/image_caption 前同步 settings→dashscope.api_key；③真实模式探针验证：买牛乃→买牛奶、收房祖→收房租、关于做产品的想法→产品创意想法（220~770ms/次）。
**教训**：真实模式跑评测前必须先探针验证 LLM 链路真的活着；静默降级会让指标归因失真。

### 2026-08-25 · 发现并修复：LLM 改写"改写伤害"→ 双路召回

**现象（第二轮 eval，LLM 真实生效）**：外部集 recall 0.886→**0.75**、hit_rate 0.914→0.771、mrr 0.90→0.77；合成集 mrr 0.8485→0.803。
**根因**：探针实锤 9/10 短关键词查询被无谓改写（"过年要给父母红包吗"→"过年是否要给父母红包"、"大明宣德年制铜香炉值多少钱"→"宣德年制铜香炉价格"），embedding 偏移致相关段落跌出 Top-3——短查询原词已是检索最优，改写即伤害。
**修复（P0-A 双路召回）**：_search_impl 在改写路之外永远保留原查询路（rewritten != q.q 时编码原查询再检索，_merge_recalls 按 content_id 取高分合并）——严格加性：纠错/扩写生效时加召回，改写有害时原路兜底，不可能比单路差。
**安全探针**：松鼠桂鱼不改写（无新误召回）；去年去的地方→去年去过的地点（时间过滤双路均为空）；买牛奶/马拉松/上个月的照片不改写。
