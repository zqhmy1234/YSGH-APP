## 2. 方法

- **脚本**：`scripts/loadtest/loadtest.py`（httpx.AsyncClient + asyncio.Semaphore 控制并发；**不用 locust**——零新重依赖、结果可控、CI/本地一致）。
- **路径 × 并发档**：4 路径（P1 auth `POST /api/v1/auth/wechat`、P2 timeline `GET /api/v1/events/timeline?level=1&status=confirmed`、P3 search `POST /api/v1/search`、P4 image `POST /api/v1/search/image`）× 4 并发档（**1/10/50/100**；1=基线校准、100=门禁档）。200 并发探测**未做**：100 并发已 100% 超时且服务端进程崩溃，200 无增量信息，建议后续（见 §7）。
- **每档流程**：warmup（每路径 10 次，P4 每张查询图 1 次填充 caption 缓存，不计入统计）→ timed run（每档 30s，100 并发档 60s；或固定请求数 1→50/10→200/50→500/100→500，取先到者）→ 统计。
- **计时口径**：客户端侧（请求发出→响应完成，真实用户体验口径），不含服务端内部计时。
- **超时**：单请求 timeout=5s（httpx）；超时计入超时率、**不计入延迟分位**（100 并发档 search/image 全部超时 → n=0，无分位数）；MAX 记录最坏样本时间戳。
- **路径隔离**：同并发档下各路径独立压（保证"search 100 并发"是真实的 100 个并发 search 请求，对硬门禁更严格），路径内参数轮换（查询词库 10 个 / 图片 3 张 / code 池 10 个）。
- **数据准备与隔离**：`scripts/loadtest/seed_data.py` 自建专用压测用户 `loadtest-seed-20260827115956`（dev mock 登录，unionid 独立）+ 文字 80 条（含查询词库）+ 照片 20 张（合成小图）+ L1 事件 3 轮（events/sync）；与真机/冒烟数据隔离；残留可接受（参照 api_smoke 历史数据先例）。
- **复现命令**：见 §7。

## 5. 门禁对照（逐项判定）

| 门禁项 | 判定 | 数据依据 |
|---|---|---|
| search P3/P4 的 P95 < 3000ms（**真实档 100 并发**） | **❌ 未达标** | P3/P4 100 并发 100% 超时（>5s），n=0；真实档单并发已 3.4–5.7s。根因：SEARCH_CONCURRENCY=4 + CPU BGE-M3 推理 + 真实 LLM 调用 + DB 池争抢（§6） |
| 错误率 < 1%、成功率 ≥ 99%（**mock 档 100 并发**） | **❌ 未达标** | search/image 成功率 0%、timeline 5.5%；仅 auth 100% 达标（§3.1） |
| 超时率 < 0.1%（100 并发） | **❌ 未达标** | mock：search/image 100%、timeline 94.5%；real：同（§3.1/3.2） |
| QPS 曲线拐点 | **观察** | search QPS 被 SEARCH_CONCURRENCY=4 钉死（1 并发 0.53 → 100 并发 18.44 且多为超时计数），无线性增长；auth/timeline 10→50 并发 QPS 微升后 100 并发受 DB 池拖累（timeline 55→19，auth 保持 50） |

**门禁结论：100 并发档整体未达标。** 1 并发基线（mock）全路径达标（search P95=2.36s < 3s ✅），但 ≥10 并发 search/image 塌陷、100 并发 DB 池耗尽并触发进程崩溃。

## 6. 瓶颈分析

### 6.1 search 内部并发上限 `SEARCH_CONCURRENCY=4`（吞吐天花板）
`recall.py` 全局 `BoundedSemaphore(4)` 包裹 `search`/`search_by_image`（P2-01 防线程池被推理占满）。任何并发 >4 的检索请求在信号量排队；配合 5s 客户端超时 → 10 并发即 98–100% 超时。**这是设计使然的保护，但成了 100 并发门禁的硬顶。**证据：L10 仅 1 个 search 样本（5044ms，恰好压线）。

### 6.2 BGE-M3 本地 CPU 推理慢（单请求 1.5–1.8s mock / 3.4–5.7s real）
`encode_query` 每次 search 执行 **两次** 完整前向（`encode_dense` + `encode_sparse`），CPU-only 机器（OMP 4 线程）单次编码 ~0.5–1s；叠加 Qdrant dense+sparse RRF 检索 + 组装 ≈ 1.5–1.8s（mock 客户端侧，服务端 latency_ms 0.9–1.2s）。真实档再叠加 qwen-flash 改写/精排（`rewritten=None` 但仍产生 LLM 往返）。**无 GPU 时单请求已接近门禁，无法支撑并发。**

### 6.3 DB 连接池 `QueuePool(size=5, overflow=10)=15` 耗尽 → 请求 30s 超时 + **进程崩溃**
100 并发下任何碰 DB 的端点（auth 登录写库 / timeline 聚合 / search 鉴权+溯源）瞬时超出 15 连接上限 → `sqlalchemy.exc.TimeoutError: QueuePool limit of size 5 overflow 10 reached, connection timed out, timeout 30.00`，该异常**未被捕获**，沿 middleware 栈上抛导致 **uvicorn 进程退出**（mock 与真实档均复现，日志见 `results/../loadtest_mock.log`、`loadtest_real.log` 与后端 stderr）。auth 在 L100 虽 100% 成功但 P95=2.4s（连接排队等待），timeline 则 89–94% 超时。**这是当前最严重的健壮性缺口（进程级故障）。**

### 6.4 BGE-M3 模型加载偶发失败（首次 search 500 / 降级）
部分服务端进程首次 search 加载 BGE-M3 时报 `Cannot copy out of meta tensor`（`torch_dtype` 弃用告警 + sentence-transformers/torch 兼容问题），导致该进程检索降级/返回 500（曾观测 mock search 错误率 1.0）。属加载路径健壮性问题，非稳态性能。

### 6.5 环境噪声（非被测代码问题，已控制影响）
压测期间机器 16GB 内存被并行 Agent 的 pytest/api_smoke/numpy 构建抢占，空闲内存一度 0.3–1GB，我的服务端进程多次被 OOM 杀（重启后重测）。报告数据取自服务端存活、模型加载成功的稳定窗口；CPU 争抢仍可能小幅抬高延迟（mock search 单并发在 1.5–2.4s 间波动）。

### 契约需求（本卡不直接改业务代码，登记供后端/集成评估）
1. **DB 连接池**：扩池（size/overflow 上调或按并发动态）**且捕获连接超时**（当前未捕获 → 进程崩溃）。P0。
2. **search 并发与超时协同**：SEARCH_CONCURRENCY=4 与客户端 5s 硬超时组合导致高并发全灭。建议评估：提高并发上限（需 GPU/并行推理支撑，否则线程池/内存吃紧）或对排队请求返回 429+`Retry-After`（限流语义）而非拖到 5s 超时。P0。
3. **查询编码优化**：`encode_query` 合并 dense+sparse 为单次前向（当前两遍 `model.encode`）。P1。
4. **生产推理形态**：BGE-M3 上 GPU（fp16 单卡可显著提升并发吞吐）或查询向量缓存。P1。
5. **模型加载健壮性**：修复 sentence-transformers `torch_dtype`/meta tensor 偶发失败，避免首次 search 500。P1。

## 7. 结论与建议 + 复现命令

**结论**：
- 核心读路径（auth/timeline）在 1–10 并发表现正常（P95 < 350ms）；50 并发 auth 开始出现 9% 超时，100 并发 timeline 89–94% 超时（DB 池瓶颈）。
- 门禁路径（search/image）：**1 并发 mock 达标（P95=2.36s < 3s）**，但 **≥10 并发即塌陷，100 并发 100% 超时 → 硬门禁未达标（❌）**。根因集中在 6.1–6.4。
- **修复优先级**：DB 池扩池 + 超时捕获（进程崩溃，P0）→ search 并发/超时协同（P0）→ GPU 推理 / 编码合并（P1）。修复后重测 100 并发。
- **200 并发探测**：建议在 DB 池与 search 并发修复后追加（当前 100 已全超时+崩溃，无增量信息）。
