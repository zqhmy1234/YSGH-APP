## 一、云打包卡点：两层根因，均已解除

### 1.1 表层：manifest.json 的 UTF-8 BOM 触发 hjson 解析失败

**现象**：`cli pack` 秒吐「打包终止」，无 APK，无有效报错文本。

**真身**（`C:\Users\ghf\AppData\Roaming\HBuilder X\.log`，两次同因）：

```
2026-09-01 18:59:11.552 [WARNING:] [PluginHost] 打包终止 Error:
  Found '{' where a key name was expected (check your syntax or use quotes if the
  key name includes {}[],: or whitespace) at line 1,1 >>>{  "name": "忆述光华", ...
    at e.exports [as parse] (...uniapp-extension\out\index.js:1:660016)
    at t.readJsonFileUncommentWritejsonFile (...index.js:12:27196)
    at async t.checkPackPromotion (...index.js:1:449232)
    at async t.validateForm (...index.js:12:168045)
    at async t.appPublish (...index.js:12:174569)
```

**定性**：解析器是 **hjson**（在 `index.js` 中 grep 到 hjson-js 的 key-name 解析器源码，
报错字符串逐字吻合）。hjson 支持**无花括号根对象**：根解析时若首字符不是 `{` 就进入
无括号模式，随后要求读 key name；此时撞上 `{` 即抛错。
UTF-8 BOM（`EF BB BF`）不算空白符（`0xFEFF > 0x20`），于是被当成"无括号对象的开头"，
`{` 反而成了非法字符。

**影响面**：全仓。`efb183d`（09-01 Vapor 迁移）引入 BOM，develop / fix/4b / wrap1 三个
分支 HEAD 全部带毒，云打包一律不可用。

## 二、D-19 重新定性：不是「manifest 未合并」，是「插件代码压根没进包」

前任（`35b6f97`）的修法＝把 FGS service 声明从插件内 manifest 迁到工程根
`client/AndroidManifest.xml`（云打包合并点）。**该机制判断正确，但层级太靠下——
更上游的问题是 UTS 插件根本没被云打包编译进去。**

### 2.0 ⭐ L1（最上游·致命）：自研 UTS 插件未被云打包识别，代码不进 dex

**实证 1**——08-28 自定义基座 APK 的 3 个 dex，忽略大小写宽搜 "yishu"，**只命中 5 个字符串**，
全部是应用包名自身产物，无任何插件类：

```
[classes2.dex] Lcom/yishu/guanghua/BuildConfig;
[classes2.dex] Lcom/yishu/guanghua/R$drawable;
[classes2.dex] Lcom/yishu/guanghua/R$string;
[classes2.dex] Lcom/yishu/guanghua/R;
[classes2.dex] com.yishu.guanghua
```

`yishu-photo-watch` / `yishu-background-tasks` / `yishu-recorder` **一个类都没有**。
作为对照，同一批 dex 里 `uts/sdk/modules/DCloudUni*/...` 命中 **501** 个（全是官方模块）。

**实证 2**——云包依赖清单 `assets/HXDependencies/uniapp-x-uts.json` 的 `duts` 数组
共 35 项，**全部是官方 `uni-*`，零个 `yishu-*`**：

```
["uni-actionSheet","uni-theme","uni-getSystemInfo","uni-base64ToArrayBuffer",
 "uni-arrayBufferToBase64","uni-crash","uni-storage","uni-dialogPage","uni-event",
 "uni-exit","uni-form","uni-form-dom1","uni-getAccessibilityInfo","uni-getAppAuthorizeSetting",
 "uni-getAppBaseInfo","uni-getDeviceInfo","uni-getElementById","uni-getSystemSetting",
 "uni-match-media","uni-modal","uni-openAppAuthorizeSetting","uni-page-container","uni-picker",
 "uni-privacy","uni-progress","uni-prompt","uni-rpx2px","uni-rich-text","uni-web-view",
 "uni-network","uni-recorder","uni-getNetworkType","uni-chooseMedia","uni-fileSystemManager",
 "uni-websocket"]
```

**成因**——三个插件的 `package.json` **缺 `uni_modules` 段**（无 `platforms`、无 `uni-app-x` 声明）：

```json
{
  "id": "yishu-photo-watch",
  "displayName": "忆述光华 · 相册监听",
  "version": "1.0.0",
  "description": "...",
  "keywords": ["photo", "observer"]
}
```

> ⚠️ **此推测已于 09-01 夜间被证伪，保留仅供溯源。**
> 官方文档（`uniapp.dcloud.io/plugin/uts-plugin`）给出的 HBuilderX 新建 UTS 插件默认
> 清单即为 `{"id":..., "displayName":..., "version":..., "description":..., "uni_modules": {}}`
> —— `uni_modules` 允许为空对象，**并非识别前提**。真正的机理见 §2.0b。

另注：三插件的 `package.json` 本身也不齐整 —— `yishu-photo-watch` /
`yishu-background-tasks` 完全无 `uni_modules` 字段；`yishu-recorder` 虽有该字段，
但 `"main": "utssdk/index.uts"` 指向一个**不存在的文件**（`utssdk/` 下只有
`app-android/` 与 `interface.uts`）。

**排除「当时插件还不存在」**：`git log --diff-filter=A` 显示
`yishu-photo-watch` 于 2026-08-24 `625cb10` 入库，另两个 08-26 入库，
均早于 08-28 17:02 的出包时点。

**结论**：**L1 不修，下面 L2–L4 改了也不进包，等于白改。**

### 2.0b ⭐⭐ 决定性尸检（09-01 新包）：插件没进 dex，而是被编译进了 **JS 层**

新包 `.wt/fix4b/client/unpackage/debug/android_debug.apk`（73,027,984 B）aapt + dex 尸检。
**这一步把 L1 的机理从"推测"变成"实证"，并推翻了"没人 import"的假设。**

#### ① 三个自研插件仍不在 dex（与 08-28 旧包一致，非偶发）

| 关键词（dex 三文件合计 20.6 MB 字节流） | 命中 |
|---|---|
| `YishuPhotoWatch` / `YishuBackgroundTasks` / `YishuRecorder` | **0 / 0 / 0** |
| `DataSyncService` / `PhotoObserver` | **0 / 0** |
| `BgTaskManager` / `BgBackground` / `initPeriodic` | **0 / 0 / 0** |
| `uts/sdk/modules/*` 命名空间 | 30 个，**全为 `DCloudUni*` 官方模块** |

#### ② 但插件代码**确实进了包** —— 只是进了 JS 层 `app-service.js`

`unpackage/dist/build/app-android/app-service.js`（317,958 B）中命中
`uni_modules/yishu-photo-watch` ×14、`uni_modules/yishu-background-tasks` ×7。
逐条看上下文，**全是编译器保留的源码位置标记**，而非 import：

```
uni.__log__("error","at uni_modules/yishu-photo-watch/utssdk/app-android/index.uts:97", ...)
uni.__log__("log",  "at uni_modules/yishu-photo-watch/utssdk/app-android/index.uts:127", ...)
uni.__log__("log",  "at uni_modules/yishu-background-tasks/utssdk/app-android/index.uts:213", ...)
```

→ **插件的 `.uts` 源码被编译成 JS 运行在 JS 引擎里，不是编译成 Kotlin 进 dex。**
其原生交互全部退化为**反射调用**（`app-service.js` 中 `Class.forName` ×3、
`getMethod` ×2、`invoke` ×2）。

#### ③ 反射目标类的 FQN 是虚构的 —— 与 D-19 同族错误的第四例

`app-service.js` 中取到硬编码常量：

```js
const MANAGER_CLASS = "uni.UNIYISHU001.BgTaskManager";   // yishu-background-tasks
```

dex 中 `BgTaskManager` 命中 **0**。而 `BgTaskManager` 的真实定义是
`uni_modules/yishu-background-tasks/utssdk/app-android/BgBackground.kt`
（UTS hybrid 混编 Kotlin 源）—— **该 .kt 文件同样没有进包**（dex `BgBackground` 命中 0）。

#### ④ 机理归纳（修正版）

```
插件 .uts  ──编译──▶  JS 层 app-service.js（在 JS 引擎跑，原生 API 只能靠 Class.forName 反射）
插件 .kt   ──✂️────▶  从未进入编译（hybrid 混编未生效）
manifest 声明 uni.UNIYISHU001.*  ──▶ 指向不存在的类（命名空间虚构）
```

**D-18「WorkManager 探测恒 false」在此得到完整解释**：
探测逻辑 `workManagerRuntimePresent()` 在 JS 层 `Class.forName("uni.UNIYISHU001.BgTaskManager")`
→ 类不存在 → 恒 false → 日志降级输出「标准基座（无 WorkManager），降级 pending + setInterval 兜底」。
**不是"探测代码写错"，是"被探测的东西从未存在"。**

**D-19 同理**：manifest 里 `uni.UNIYISHU001.DataSyncService` 在 dex 中命中 0，
`startService()` 必然 ClassNotFoundException。

#### ⑤ 已验证成立的部分（前任修法没错，只是层级不够）

| 项 | 尸检结果 |
|---|---|
| 工程根 `client/AndroidManifest.xml` 合并进云包 | ✅ `service android:name="uni.UNIYISHU001.DataSyncService"` 已入包（旧包无此项） |
| FGS 权限三件套 | ✅ `FOREGROUND_SERVICE` / `FOREGROUND_SERVICE_DATA_SYNC` / `POST_NOTIFICATIONS` 均已声明 |
| D-18 marker 资产 | ✅ `assets/yishu/workmanager-marker.txt` 已入包（nativeResources 机制成立） |
| `__UNI__2650A2A` 身份 | ✅ manifest meta `DCLOUD_UNI_APPID = __UNI__2650A2A` |
| 包名/版本 | ✅ `com.yishu.guanghua` v100 / 0.1.0，targetSdk 34，minSdk 24 |

→ **载体机制全部打通，缺的是"被承载的原生代码本身"。**

### 2.1 实证：UTS 插件类的命名空间铁律

对 08-28 旧 APK 的三个 dex 全量正则扫描：

| 命名空间模式 | 命中数 |
|---|---|
| `uni/UNI<APPID>/...` | **0** |
| `uts/sdk/modules/<驼峰插件名>/...` | **501** |

→ UTS 插件类编译后落在 **`uts.sdk.modules.<插件目录名驼峰>`**，与 appid 无关。
本项目插件目录 `yishu-photo-watch` → 驼峰 `YishuPhotoWatch`。

### 2.2 L2–L4：即便代码进了包，FGS 实现本身也是「鸭子类型冒充」（均在 `uni_modules/yishu-photo-watch/utssdk/app-android/index.uts`）

> ⚠️ 以下三项独立于 L1，**都必须修**；但只有先修 L1，它们才会真正进包生效。

| # | 位置 | 现状 | 正确做法 |
|---|---|---|---|
| 1 | `index.uts:235` | `class DataSyncService { constructor(){ super() } }`——**无 extends**，是普通 UTS 类，不是 Android 组件 | `import Service from "android.app.Service"` + `class DataSyncService extends Service`，生命周期方法加 `override` |
| 2 | `index.uts:36` `SERVICE_CLASS_FQN` | `uni.UNIYISHU001.DataSyncService` | `uts.sdk.modules.YishuPhotoWatch.DataSyncService` |
| 3 | 工程根 `AndroidManifest.xml:29` / 插件内 manifest | 同 #2 的错误类名 | `uts.sdk.modules.YishuPhotoWatch.DataSyncService` |
| 4 | `index.uts:373-405` 启停 | 用**对象字面量冒充 Intent**（`{ setClassName: function(...){return this} }`）传给 `startService()`；且 Android 8+ 前台服务须 `startForegroundService` | `new Intent(UTSAndroid.getUniActivity(), UTSAndroid.getJavaClass(DataSyncService()))` + `startForegroundService()` |

**旁证**：旧 APK 三个 dex 全量扫 `DataSyncService` 字符串命中 0 —— 该类在 08-28 时确实还不存在
（D-19 修复代码写于 08-29），与台账「dex 尸检：类全在包里」不矛盾（那句指的是 WorkManager 类，
不是 Service）。

**旁证 2**（权威案例，CSDN 145777442，2025-02-21 发布 / 2026-08 仍更新）：
> 这里 service 包名前缀为 `uts.sdk.modules` 不可改动，因为我们是 modules 形式插件，
> 然后 `myToast` 是你插件命名的驼峰标识… **包名不对会导致无法正确启动服务**。

### 2.2b 同病：相册监听 `PhotoObserver` 也未继承原生类

`index.uts:102` 注释写着「UTS 继承原生类（POC-01 路径）」，但实际：

```uts
class PhotoObserver {            // ← 没有 extends ContentObserver
	onChange(selfChange: boolean, uri: any | null): void { ... }
}
```

而它被直接传给需要真 `ContentObserver` 的
`getContentResolver().registerContentObserver(uri, true, this.observer)`（`:351`）。
与 L3 同一病症，**相册监听能力本身也很可能从未真正生效**（待真机复验坐实）。

### 2.3 结论

**D-19 状态「已修待复验」不成立，且原修法层级不够。** 即使工程根 manifest 合并生效：

1. 插件代码不在 dex 里（L1）→ `DataSyncService` 类根本不存在；
2. 即便存在，`uni.UNIYISHU001.DataSyncService` 也不是 Service 子类（L2/L3）；
3. 即便类是 Service，假 Intent 会先一步崩掉调用（L4）。

R2 电池组第 1 项（D-18/19：logcat 见 `initBackgroundTasks ok` + 前台服务通知在场）
**在当前代码下必然 FAIL**。同理，D-18 的 WorkManager 探测恒 false，
根因也是 L1（插件没进包）——不是探针写法问题。

R2 电池组第 1 项（D-18/19 logcat 见 `initBackgroundTasks ok` + 前台服务通知在场）
**在当前代码下必然 FAIL**，除非先按 §2.2 四项改正并重新出包。

### 2.4 候选处置（待峰宝拍板）

**修复顺序不可颠倒：L1 → L2 → L3 → L4。L1 是闸口。**

| 层 | 修复动作 | 文件 |

| L3 | `class DataSyncService extends Service`（生命周期方法加 `override`）；`class PhotoObserver extends ContentObserver` | `index.uts:235` / `:103` |
| L4 | 启停用 `new Intent(UTSAndroid.getUniActivity(), UTSAndroid.getJavaClass(DataSyncService()))` + API26+ 走 `startForegroundService`；通知改真 `NotificationChannel`/`NotificationCompat.Builder` | `index.uts:263-312`、`:373-405` |

| 方案 | 内容 | 代价 / 判断 |
|---|---|---|
| **A（推荐）** | L1→L4 全修，一次重出包 | 改 5 个文件，重出包一次（约 10–20 分钟排队）；修完 D-18/D-19 才有可能真绿 |

## 四、L1 根因定案与修复进展（21:15-21:30）

### 4.1 金标准：HBuilderX 内置 UTS 插件模板

**`D:/HBuilderX/plugins/uni_modules/lib/uts-api/package.json`** —— 这是 HBuilderX「新建 UTS 插件」
使用的模板，也是判定"什么才算一个 UTS 原生插件"的唯一权威。其 `uni_modules` 块：

```json
"uni_modules": {
  "dependencies": [], "encrypt": [],
  "platforms": { "cloud": {...},
    "client": {
      "uni-app":  { "vue": {...}, "web": {...}, "app": {...}, "mp": {...}, "quickapp": {...} },
      "uni-app-x": { "web": {...}, "app": { "android": "-", "ios": "-", "harmony": "-" }, "mp": {...} }
    } } }
```

**决定性字段**：`uni_modules.platforms.client["uni-app-x"].app.android`。
另有 `engines`（含 `"uni-app-x": "^3.1.0"`）与 `dcloudext.type: "uts"`。
模板目录还含 `utssdk/app-android/config.json`（最小集 `{"minSdkVersion":"21"}`）。

### 4.2 我方三插件的差距（= L1 根因）

| 插件 | `uni_modules.platforms` | `engines` | `dcloudext.type` | `config.json` | `main` |
