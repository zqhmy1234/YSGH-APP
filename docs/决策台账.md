## §4.18 环境配置漂移根治 · 新包全站不可用的头号根因（2026-10-11）

**现象**：重构后的新包「各个页面都无法正常体验、页面之间的数据流与控制流像是被切断」。

**根因（实锤，带 git 证据）**：`client/utils/config.uts` 的环境三件套**随代码提交漂移**：

| 项 | 9-23（重构前 · 老包可用） | 10-09 之后（新包） |
|---|---|---|
| `ENV` | `'prod'` | `'dev'` ← 在 `c356781`「壳内空态重构」提交里被连同真机联调改动一起改掉 |
| `REAL_DEVICE_HOST` | `''`（空串） | `'localhost'` |
| `PROD_BASE_URL` | 公网 IP（出包时填） | 临时隧道地址 |

⇒ 任何打包产物内 `getBaseUrl()` 都返回 `http://127.0.0.1:8010`（**手机自己的回环地址**，空无一物）
⇒ 所有接口失败 ⇒ 每个页面都取不到数据、跳转后目标页同样空 ⇒ 表现成整体性的「数据流被打断」；
而 release 包 console 不可见 ⇒ 现场无从下手（本项目最贵的一类故障，与文件头 8010 抢占事故同源）。

**根治（不只把常量改回去——那样下次联调还会漂移）**：`getBaseUrl()` 增设运行时判据
`isDevCarrier()`（按 Android 包名识别 HBuilderX 开发载体 `io.dcloud.uniappx`）——
**打包产物一律不允许走 dev 地址**：即便 `ENV` 误留 `'dev'`，也强制走 `PROD_BASE_URL`
并 `console.error` 告警（`_devEnvInPackageWarned` 只喊一次）。
效果：「忘改 ENV」从**新包全挂**降级为**新包照常可用**；真机联调完全不受影响
（标准基座内仍走 localhost + `adb reverse`）。取不到包名时保守按打包产物处理（安全侧）。

**双保险（出包流程侧）**：`scripts/preflight_pack.ps1` 已拦占位词/回环地址/临时隧道域名
（隧道词 2026-10-11 补）；出包前仍必须把 `ENV` 改回 `'prod'` 并填真实公网地址。

**同类登记（同批，视觉/数据完整性）**：
- 令牌误映射 11 处已按 9-23 恢复（见 `styles/*.css` 内注释与 `.cowork-temp/audit-css2-out.txt`）；
  74 条 Δ≤1/255 的设计基色归并**保留**（令牌值取自画布实测真源，改回字面量的可维护成本更高），
  已在 `design_tokens.dtcg.json` 的 `alpha.ink.$description` 写明核对结论与撤销项。

**⑩c 批次 5 续（2026-10-14）· 播放态写入降频（RC-1）与上传横幅响应式（RC-12）**

**RC-1（模板函数插值 × 33ms 时钟）**：`audio_player` 的进度时钟 **33ms 一跳（30Hz）**，而
`voiceProgress` 是**每跳都在变的浮点数** ⇒ 每跳触发一次响应式通知 ⇒ 时间轴里所有语音卡的**模板
函数调用**（`voiceProgressOfCard(cid)` 等，每卡 4~6 个）与进度条 `:style="{width:%}"` 全部重算重排
——50 张照片的列表里只要有一张语音卡在播，就是**每秒 30 次全列表重算**。
**修法**：**相等守卫 + 1% 粒度**——只有变化 ≥1% 才写（`p >= 1.0` 强制收尾）。1% 细于波形染色条的
单条粒度（28 条 ≈ 3.6%/条），视觉无差别，写入频次降到约 **1/10~1/18**（60s 音频 ≈ 1.7 次/秒）。
注：`voiceCurSec` 用 `Math.round` ⇒ 同秒内重复赋同值，Vue 的 `ref` **同值不触发**，本就不是热点；
真正的热点只有 `voiceProgress`。

**RC-1 明确未做（不隐瞒）**：把 `:style="{width:%}"` 改 `transform: scaleX` 与"预计算进卡片属性"的
完整重写。理由：经上述守卫后残余成本已可忽略（~1.7 次/秒 × 每卡约 5 个函数调用），而 `scaleX`
依赖 `transform-origin: left` 在 uvue App-Android 的支持——**若不生效，进度条会从中间向两侧长**，
而这类视觉缺陷**编译门查不出、只能真机发现**。风险高于收益 ⇒ 留待真机可验证时再做。

**RC-12（`UploadStatusBanner` 裸 `let` 非响应式）**：6 个状态（`paused`／`pauseReason`／`held`／
`failed`／`uploading`／`netKind`）全为**裸 `let`**，而 5 个 computed **直接读它们** ⇒ computed
**没有响应式依赖** ⇒ 首次求值后**永久缓存** ⇒ 横幅只在首帧判断一次，3s 轮询写入的值**界面永不反映**
（表现即"该出现的横幅不出现"）。**修法**：全部改 `ref`，并在**所有**读取处补 `.value`（含 5 个
computed 与点击处理 `onBannerTap`／`onActionTap`／`doContinue`——**裸读会拿到 Ref 对象恒为真**，属必修项）。
**⚠️ 过程中的一次自我更正**：我起初只读了 `refresh()` 就断言"`uploading` 从未被赋值 ⇒ 该档恒不可达"，
读到点击处理才发现它在 `doContinue` 里被**真实置位** ⇒ **当场撤回该判断并保留第四档**（不用"删代码"
掩盖我读漏的范围）。

**验证**：编译门**真编译**通过（35.1s / 42.2s）；裸读残留扫描无命中。

**⑩e 批次 5 续（2026-10-14）· 流式逐帧与滚动锚点（RC-8）**

**问题（两处）**：
① `chat_api` 的**预览帧按 token/chunk 到达**（每秒可达数十帧），而原实现**每帧直接写**
`chatStreamText`（TabAi 的 typing 气泡绑它渲染）⇒ **每帧一次 TabAi 重渲染**，而打字机气泡处在
`v-for` 消息列表内 ⇒ **整列表跟着重渲染**（长会话即"打字卡顿、输入滞涩"）。
② `scrollToBottom` **无条件** `scrollInto=''` → 50ms 后设值 ⇒ **每次滚动两轮布局**。

**修法**：
① **合帧落定**：新文本先暂存到**非响应式**变量，最多每 **80ms** 落一次 ref（≈12.5Hz，对"逐字"
观感足够）⇒ 重渲染次数降到约 1/N。**安全边界（必须成对）**：每轮**开始**（`sendChatMessage`）与
**结束**（该 promise settle）都 `cancelStreamTextFlush()`——否则调用方收到终稿并清空 ref 之后，
残留定时器会把**上一轮尾句写回去**（"回复闪回"）。`replace` 帧与 `preview` 同入口，天然覆盖。
② **只在"锚点未变"时才清空重设**：锚点变化（新消息上屏）时一次赋值即触发，省掉清空与 50ms 延迟；
同锚点重复滚（气泡长高、id 不变）才走"先清再设"。

**评估后明确不改（RC-6）**：`VoiceWave` 的 50ms 呼吸时钟**已带 `props.active && voicePlaying` 守卫**，

⇒ 每 tick 真正产生新串的只有"分界 ±1 与呼吸 bar"两三根。**不是热点；动它只会降低动效平滑度**。

**⑫ RC-7 已落成（2026-10-14）· ST-DBSCAN 算法性能（语义逐位等价的剪枝）**

**问题**：`client/utils/agg/st_dbscan.uts` 是端侧 L0 聚类核心，旧实现是**双重全表扫描**（外层每个
未访问点扫一遍全表、簇内每个新点再扫一遍）⇒ **O(n²) 次 `isNeighbor`**，每次含 haversine
（sin/cos/asin）；而 `agg_runner` 在**上传完成回调里同步调用**它（UTS 无 worker）⇒ n 一大就卡死
JS 线程（用户感知：列表掉帧、点击没反应）。

**三层优化（都不改判定，只少看"不可能的点"）：**

| 层 | 手段 | 效果（**判定次数**，机器无关） |
|---|---|---|
| ① 时间窗剪枝 | 邻居的必要条件是 \|Δt\| ≤ εt ⇒ 按下标按 ts 排序 + 双指针求窗 | 散开型 n=1500：2,248,500 → **0** |
| ② 空间盒预筛 | 窗内**两边都有 GPS** 时先用保守经纬度盒挡掉明显超距者（免算 haversine） | 现实形态 n=8000：64M → **69,251** |
| ③ **团快路** | 整窗若能被**证明两两皆邻居**（时间跨度 ≤ εt 且 GPS 子集落在"半盒"内）⇒ O(k) 直接给全集 | 同地连拍 n=720：517,680 → **0** |
| ④ 顺序还原 | 候选按**原始下标升序**回排（DBSCAN 边界点归属依赖遍历顺序）⇒ 结果**逐位一致** | 139 用例 **0 失败** |

**"可达最坏形态"的推导（重要）**：`pipeline.preprocess` 有**连拍折叠**（间隔 <5s 折叠为 1 个时间点）
⇒ 单一 60min 窗内可达点数上界 ≈ **3600 / 5 = 720**。故性能承诺以**可达**输入为基准——我最初构造的
n=1500 同地连拍基准**其实不可达**，已据实修正（不拿不可达输入吓人，也不拿它当挡箭牌）。

**取证（`scripts/bench_st_dbscan.py`，可复跑）**：
- **等价性**：与仓库权威参考端（`backend/app/services/event_aggregation/st_dbscan.py`，AGG-016 夹具的
  产出方）在 **19 边界 + 120 随机模糊 = 139 用例**上**逐位对拍**、**0 失败**；边界含时间窗整数秒 /
  距离 ±1m / 跨 ±180 经线 / 全无 GPS 与混合 / 极区（cos 保护）/ 以及**团快路专用边界**
  （半盒内、一维越界、时间跨度超窗、对角铺满半盒）。
- **性能**：以上表**判定次数**为准（机器无关）；Python 墙钟仅供参考——"大量数组构造但零 trig"的形态
  会被 Python 放大数倍到数十倍（设备上是 JS）。
- **诚实边界**：基准里的剪枝版是 **Python 镜像**（与 UTS 逐行对齐），证明的是**算法等价性与量级**；
  端侧真等价仍以 AGG-016 双跑（`gen_agg_fixtures.py` → agg-check 页）为准。

**可观测**：UTS 内留下 `[yishu-agg] stDbscan n=… 判定=… 团快路命中=… 全扫基准=… 耗时=…ms`；
判定次数超 **20 万**时 `console.warn` 显式告警（"会喊的界"——不让它静默变慢）。
