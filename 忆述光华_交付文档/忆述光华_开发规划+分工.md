## 七、风险与缓冲（4 人→7 人后变化）

| 风险 | 影响 | 缓冲策略 |
|---|---|---|
| **UTS 原生缺口 + 事件聚合门禁**（仍最高） | 客户端线受阻 | POC 五测 W2 结论；聚合降级"端侧粗聚类+服务端精聚合"；切原生/Flutter 路径已备 |
| **关键人单点**（T1/T2 任一缺席） | 主线停 | 交叉 review；T3 向 T2 学核心；契约/文档先行降交接成本 |
| **产品侧交付延迟**（标注/设计稿/文案） | M1/M2 卡点 | P3 标注 LLM 合成兜底；P2 设计稿 W6 硬节点（AI 出初稿提速）；P1 验收 W2 拍板 |
| 企微认证慢 | M3 卡死 | W1 第一天申请；认证期并行写沙箱 |
| 事件聚合不达标 | M2 延期 | 原型三重前置（W1 spike→W3 Python→W7 UTS）；门禁拆两段 |
| 范围蔓延 | 什么都做不好 | Non-goals 清单为准 |

**缓冲机制**：每阶段预留 15% 时间余量；总周期 19 周 + 15% ≈ **22 周**。

**一句话**：7 人 = 4 技术三线并行（后端 A / 客户端 B / Windows+运维 C）+ 3 产品两条供给线（P1 决策线、P2/P3 内容与数据线）；全局 Gate 是 **T2 的 POC（W2）** 和 **P1 的验收拍板（W2）**，两条线都卡在 M0——M0 是所有人的起点，也是所有人最早的对齐点。
